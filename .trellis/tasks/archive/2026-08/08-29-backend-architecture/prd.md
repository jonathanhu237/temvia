# Plan Go backend architecture

## Goal

Plan a backend-only first-administrator setup and login milestone for Temvia's generated Go API, informed by the Clean Architecture discussion. The current task must establish and verify the HTTP contract, persistence, sessions, migrations, configuration, and container infrastructure without modifying the generated React admin. Browser pages and frontend integration will be planned and implemented in a separate follow-up task.

## Background

- The user approved creating this planning task on 2026-08-29 and explicitly requested an explanation of Clean Architecture before proceeding with architecture selection.
- The user acknowledged understanding Clean Architecture, considered a User API, and then clarified the desired first feature: a page for entering the initial administrator's information, followed by login using that administrator's credentials. This supersedes the open choice between a disposable User example and a real account feature.
- The user requires every technical choice to be discussed explicitly. After reviewing established open-source projects and clarifying the proposed link-based flow, the user accepted a deployment-issued temporary initialization link on 2026-08-29. This accepts that initialization experience only, not the remaining technology choices or implementation.
- The user clarified that generated applications may be initialized on either private networks or the public internet. Planning must not assume a private-only setup environment or ask the user to choose one exclusive deployment environment.
- After discussing MySQL compatibility, the user clarified that Temvia is for personal use, has no MySQL-only deployment requirement, and prefers PostgreSQL. The first milestone therefore targets PostgreSQL only, as recorded in R14. After comparing access interfaces, the user prioritized standard-library API stability and selected database/sql under R15, then explicitly accepted pgx/v5/stdlib as its underlying PostgreSQL driver under R16.
- Temvia scaffolds independent Go API and React admin applications. The API is the application's general backend, not exclusively an admin backend; see `.trellis/tasks/archive/2026-08/08-28-starter-cli-planning/prd.md:23`.
- The current backend consists of a standard-library HTTP server and `GET /health` in `template/api/cmd/server/main.go:10`, with health and routing tests in `template/api/cmd/server/main_test.go:10`.
- The current template has no business API, database, authentication, or selected business architecture. The initial minimal backend contract is recorded in `.trellis/spec/backend/scaffolding-contract.md`.
- On 2026-08-30, the user stated a preference that values intended to be configurable should be placed in `.env` wherever practical. The repository already ignores `.env` and `.env.*` while allowing `.env.example`; exact scope, secret handling, validation, and loading responsibilities remain under discussion rather than making every internal or security constant configurable by implication.
- On 2026-08-30, the user rejected determining all public-URL requirements solely from the hostname and requested explicit development and production modes in `.env`, with different requirements. The exact mode variable and behavioral differences remain under discussion; development mode must not silently imply disabling core authentication controls.
- On 2026-08-30, the user challenged the proposed API command packaging because Temvia itself is a project-template generator. The assistant's placeholder name `temvia-api` obscured the generator/runtime boundary and overcomplicated the generated application. R62 supersedes only R59's command-based issuance trigger; R59's token and atomic-completion safety properties remain accepted.
- After reviewing the first concrete feature-oriented Clean Architecture proposal, the user stated that the structure was not yet understandable and questioned whether Clean Architecture is actually the right architecture. The proposal in `research/architecture-options.md` remains unselected. Planning must compare its concrete request flow and costs with simpler alternatives before asking the user to accept package boundaries.
- The user reported having previously encountered the discussed Handler/Service/Repository failure modes and subsequently moving to DDD, then requested a comparison of current successful open-source project architectures. `research/open-source-go-architecture-comparison.md` inspects Miniflux, Gitea, Mattermost, Grafana, and ZITADEL. No architecture is selected by this research.

They are deciding whether Clean Architecture or Hexagonal Architecture would provide a better long-term boundary. Treat DDD modeling, HSR request roles, dependency architecture, module organization, and deployment topology as compatible dimensions rather than mutually exclusive branded choices.
- After asking why the proposed package tree did not retain `handler` and `service` names, the user accepted the boundary-oriented naming rationale and explicitly preferred the original proposal without a familiarity-driven compromise. Package names should communicate `domain`, `application`, and concrete adapter boundaries; do not recreate generic `handler` or `service` package buckets merely to resemble the earlier HSR layout.
- After accepting the coarse setup-status API, the user requested deferring React setup/login page implementation because the frontend has its own technology stack and the backend/infrastructure milestone is already complex. On 2026-08-30 the user accepted R72's backend-only split: keep the frontend untouched in the current task, fully specify and verify the HTTP contract through automated tests and documented `curl` examples, and plan browser routing/forms/state in a separate follow-up task.
