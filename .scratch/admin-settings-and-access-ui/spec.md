# 管理端外观、语言与角色、用户管理交互

Status: resolved
Labels: ready-for-agent

本次增补范围：仅调整认证页与 Dashboard 的外观、语言入口。此前的主题能力、表格、弹窗、草稿、查询及乐观锁改造已完成；下述双按钮入口也已实现。

## Problem Statement

管理端原先不支持切换明亮与暗黑模式或跟随系统外观，这些能力现已实现。当前认证页却把外观和语言放在同一个带有语言图标及当前语言文字的按钮下，用户在点击之前无法知道其中包含外观设置。给展开后的菜单项增加图标或当前值仍然不能解决这个入口误导。用户希望外观和语言分别有独立、可见的按钮，并在认证页与 Dashboard 保持一致，同时为未来的账号设置保留清晰的入口边界。

角色管理目前采用列表与常驻编辑表单并列的布局；用户管理同时展示邀请表单、用户卡片、角色分配控件和待处理邀请。查看数据与编辑数据混在一起，页面拥挤，创建、编辑和邀请缺少一致的开始与结束方式。用户希望使用表格浏览概要，按需打开弹窗执行操作，并能搜索、排序全部相关记录。

表单输入目前依赖组件生命周期，关闭表单、切换记录或离开页面可能丢失修改。用户希望稍后继续填写，同时保留既有的并发修改保护：当其他管理员已经更新同一记录时，旧草稿不能覆盖其结果。邀请邮件语言还被锁定为操作者的界面语言，无法为使用另一种语言的收件人单独选择。

## Solution

登录页、初始化、密码恢复及接受邀请等认证页面在标题区域右侧并排提供两个独立按钮：外观、语言。Dashboard 在全局顶栏右上角提供相同顺序和含义的两个按钮，用户无需先打开头像菜单即可发现它们。点击外观按钮直接打开明亮、暗黑和跟随系统选项；点击语言按钮直接打开简体中文与英文选项，不再经过合并菜单中的分类层。头像菜单保留账户相关内容。

颜色模式默认跟随系统。外观和语言偏好立即生效并保存在当前浏览器，刷新或再次访问后恢复；本次入口调整继续使用已有偏好及其保存方式。整个管理端的页面、表格、弹窗及反馈都遵循同一外观和当前界面语言。

角色、用户和待处理邀请统一使用 shadcn Data Table 展示概要。创建角色、编辑角色、邀请用户和修改用户角色分别使用弹窗；系统角色和只读用户保持既有权限限制。用户与邀请列表支持服务端全局搜索、排序和前后翻页，角色列表基于完整数据提供名称搜索与排序。

邀请邮件语言可以在邀请表单中独立选择，初始值取创建该草稿时的界面语言。之后切换界面语言不会覆盖邮件语言选择，也不会改写已经发出的请求。

使用 Zustand 保存内存草稿。关闭弹窗或切换管理页面后可以恢复输入和选项，刷新后清空；成功提交、主动重置和退出账号按各自范围清理草稿。关闭正在提交的弹窗不会重复执行或取消原操作。

角色编辑和用户角色分配沿用已有乐观锁。草稿始终绑定开始编辑时的版本；提交版本过期时，服务器拒绝写入，界面保留草稿并说明冲突。只有用户主动选择“放弃草稿并重新载入”后，才用最新数据与版本替换草稿。

## User Stories

1. 作为管理端用户，我希望可以选择明亮或暗黑模式，以便在不同光照环境下舒适地使用界面。
2. 作为首次访问的用户，我希望颜色模式默认跟随系统，以便无需先调整偏好即可获得熟悉的外观。
3. 作为选择跟随系统的用户，我希望系统外观变化时页面及时更新，以便管理端保持一致。
4. 作为明确选择明亮或暗黑模式的用户，我希望系统变化不覆盖我的选择，以便使用我指定的外观。
5. 作为管理端用户，我希望刷新或再次访问后恢复当前浏览器的主题和语言，以便不必反复选择。
6. 作为使用多个标签页的用户，我希望同一浏览器、同一站点的偏好保持一致，以便切换标签页时不会混用外观或语言。
7. 作为在不同设备工作的用户，我希望浏览器偏好只作用于当前浏览器，以便每个使用环境独立设置。
8. 作为已登录用户，我希望从 Dashboard 顶栏右上角的两个独立按钮调整颜色模式和语言，以便无需展开头像菜单就能找到这两项偏好。
9. 作为未登录用户，我希望在登录、初始化、密码恢复和接受邀请页面看到独立的外观与语言按钮，以便完成进入系统前的操作。
10. 作为只读用户，我希望能调整自己的界面偏好，以便这项能力不受管理权限限制。
11. 作为管理端用户，我希望页面、表格、弹窗、菜单和反馈使用一致的主题，以便不会出现局部仍停留在另一种模式的情况。
12. 作为切换语言的用户，我希望仍显示的系统提示立即使用当前语言，以便准确理解错误和操作结果。
13. 作为正在填写表单的用户，我希望切换语言时保留输入、选项及已有校验状态，以便继续当前工作。
14. 作为正在等待请求结果的用户，我希望语言变化不会取消或重复请求，结果按当前语言展示，以便可靠地完成操作。
15. 作为查看角色的用户，我希望通过表格看到名称、描述、类型、权限数量和关联数量，以便快速理解角色用途。
16. 作为查看角色的用户，我希望按名称搜索角色并对概要列排序，以便找到需要查看或管理的角色。
17. 作为管理员，我希望点击创建角色后打开独立表单弹窗，以便专注填写并保持列表整洁。
18. 作为管理员，我希望从角色行打开编辑弹窗，以便明确正在修改的对象。
19. 作为管理员，我希望角色权限继续按资源分组展示，以便理解每组选项的作用。
20. 作为查看系统角色的用户，我希望能查看其内容并明确知道它不可修改或删除，以便避免无效操作。
21. 作为只读用户，我希望能够浏览获准查看的角色和用户，而不会看到可执行的管理入口，以便界面准确反映我的权限。
22. 作为填写管理表单的用户，我希望字段错误和提交错误出现在对应弹窗内，以便直接定位问题并修改。
23. 作为查看用户的管理员，我希望通过表格查看姓名、邮箱和角色，以便集中浏览已激活用户。
24. 作为管理员，我希望从用户行打开角色分配弹窗，以便页面无需常驻每个用户的编辑控件。
25. 作为管理员，我希望角色分配继续遵循现有业务约束，以便界面调整不会改变权限规则。
26. 作为管理员，我希望用户与待处理邀请分别展示，以便分清已激活账户和仍需处理的邀请。
27. 作为管理员，我希望在邀请弹窗中填写姓名、邮箱、角色和邮件语言，以便完成一个明确的邀请流程。
28. 作为邀请者，我希望单独选择邀请邮件语言，以便给收件人发送其能够理解的邮件。
29. 作为邀请者，我希望新邀请草稿默认使用当前界面语言，以便常见情形无需额外选择。
30. 作为邀请者，我希望之后切换界面语言不改变已经选定的邀请邮件语言，以便保持对收件人的选择。
31. 作为管理员，我希望邀请表显示收件人、角色、邮件语言和到期时间，以便判断后续操作。
32. 作为管理员，我希望能从邀请行重发或撤销邀请，以便继续使用现有邀请管理能力。
33. 作为管理员，我希望重发沿用该邀请的邮件语言，以便不受当前操作者界面语言影响。
34. 作为管理员，我希望删除角色或撤销邀请前看到明确的应用内确认，以便确认操作对象与后果。
35. 作为查找用户或邀请的管理员，我希望按姓名或邮箱搜索全部可见记录，以便找到当前页之外的数据。
36. 作为输入搜索词的管理员，我希望搜索忽略大小写，并按普通文字理解输入字符，以便搜索行为可预测。
37. 作为管理员，我希望用户和邀请可以按姓名、邮箱或创建时间排序，邀请还可以按到期时间排序，以便按任务需要浏览。
38. 作为查看用户或邀请的管理员，我希望默认先看到最新创建的记录，以便找到刚完成的操作。
39. 作为翻页浏览的管理员，我希望过滤和排序先作用于全部结果，再进行分页，以便各页遵循同一查询规则。
40. 作为翻页浏览的管理员，我希望相同排序值的记录保持稳定次序，以便在数据未变化时不会遗漏或重复浏览。
41. 作为修改搜索或排序条件的管理员，我希望结果回到第一页，以便不沿用失效的翻页位置。
42. 作为查看用户与邀请的管理员，我希望两个列表各自保留查询及翻页状态，以便操作一个列表不会扰乱另一个。
43. 作为遇到空结果或请求失败的用户，我希望看到明确的空态、加载反馈和重试入口，以便理解当前结果。
44. 作为键盘或窄屏设备用户，我希望表格、菜单和弹窗中的主要内容与操作可达，以便完成相同任务。
45. 作为填写表单的管理员，我希望直接关闭弹窗后仍保留草稿，以便不必在关闭时决定是否放弃修改。
46. 作为临时切换管理页面的管理员，我希望返回并重新打开后继续原草稿，以便处理其他事情后接着填写。
47. 作为编辑多个对象的管理员，我希望不同角色和用户的草稿相互独立，以便不会串用修改内容。
48. 作为管理员，我希望可以主动重置某份草稿，以便明确地重新开始填写。
49. 作为成功提交表单的管理员，我希望对应草稿清除、弹窗关闭并更新列表，以便确认操作已经完成。
50. 作为提交失败的管理员，我希望输入和选择保留，以便修正问题或重新尝试。
51. 作为提交中关闭弹窗的管理员，我希望原请求继续，重开后仍能看到提交状态，以便避免重复提交。
52. 作为管理员，我希望刷新浏览器后清除这些临时草稿，以便其生命周期符合已约定的内存保存方式。
53. 作为退出账号的管理员，我希望清除业务草稿并保留浏览器外观和语言偏好，以便结束当前账号的工作状态。
54. 作为切换账号的用户，我希望不会看到上一账号的草稿或管理列表缓存，以便界面属于当前操作者。
55. 作为遇到临时网络故障或退出失败的管理员，我希望仍保留草稿，以便可以恢复操作。
56. 作为与其他管理员同时编辑的用户，我希望过期版本的提交被拒绝，以便我的旧输入不会覆盖对方的新修改。
57. 作为收到版本冲突的管理员，我希望草稿仍然可查看并且错误清晰，以便决定如何处理自己的修改。
58. 作为主动重新载入的管理员，我希望输入和编辑基线一起更新为最新记录，以便之后能正常修改并提交。
59. 作为保留编辑草稿的管理员，我希望后台刷新不会静默替换输入或升级提交版本，以便并发修改保护始终有效。
60. 作为在请求返回前开始其他操作的管理员，我希望迟到结果只影响它对应的草稿，以便新草稿或另一账号的数据不会被误清除。
61. 作为首次访问登录页的用户，我希望在未展开任何菜单时就能辨认外观与语言入口，以便不用猜测语言按钮中是否还有其他功能。
62. 作为调整偏好的用户，我希望点击每个按钮后直接看到它对应的选项，以便只需打开一次菜单就能选择。
63. 作为从登录页进入 Dashboard 的用户，我希望两个按钮保持相同的顺序和含义，以便沿用已经学会的操作方式。
64. 作为键盘或窄屏设备用户，我希望两个按钮仍然分别可达且不会挤压页面标题和主要操作，以便在不同使用环境下独立调整外观与语言。

## Implementation Decisions

- **实施范围**：修改管理端应用模板及其配套 API，覆盖主题与语言入口、角色表格、用户表格、邀请表格、四类业务表单弹窗、草稿状态和全局查询。实现不需要改变脚手架生成流程。
- **本次入口增补范围**：仅修改管理端共享偏好控件、认证页面框架、Dashboard 全局顶栏及相关交互测试。保留已完成的业务改造，不扩展 API、数据库或偏好持久化协议。
- **组件选择**：沿用现有 React、Tailwind、shadcn/Radix 体系。用 shadcn Table 与 TanStack Table 组织 Data Table，用 Dialog 承载表单，用应用内确认弹窗承载删除和撤销确认。组件扩展遵循现有项目约定，不切换组件基础体系。
- **主题状态**：主题偏好取明亮、暗黑或跟随系统。初始化优先使用有效的浏览器已保存选择，否则跟随系统；系统模式监听系统外观变化，显式模式不受其覆盖。初始化应尽早应用正确外观，避免明显的错误主题闪烁。
- **主题覆盖**：通过共享语义颜色统一处理页面、认证界面、表格、弹窗、菜单及通知反馈；移除通知区域固定浅色的行为。主题变化不会重挂载业务表单。
- **偏好入口布局**：认证页面标题区域右侧和 Dashboard 全局顶栏右上角均并排展示外观、语言两个独立按钮，顺序一致。Dashboard 的主页、用户页和角色页复用同一顶栏入口，不依赖侧栏展开状态或管理权限。取消将两项偏好收在单个语言按钮下的入口。
- **偏好按钮与菜单**：外观按钮使用可辨认的太阳／月亮图标，并提供“外观设置”的可访问名称及悬停、键盘聚焦提示；语言按钮使用语言图标和当前语言文字，并提供“语言设置”的可访问名称。每个按钮单独打开对应的选项菜单，当前选择有明确标记。打开菜单不修改偏好；选择后立即生效。窄屏可收起当前语言文字，但仍保留两个独立可见的按钮及其名称，不合并为一个入口。
- **头像菜单边界**：移除头像菜单中的外观与语言入口，保留既有账户信息和退出登录操作。个人资料、修改密码等未来账户功能属于该菜单的后续范围，本次不新增功能或占位项。
- **偏好保存**：沿用现有浏览器保存值，选择后立即保存，不另设保存步骤。偏好仅在当前浏览器生效；同源标签页同步偏好，登录或退出不清除它们。浏览器存储不可用时仍允许当前页面切换。
- **语言规则**：保持已保存选择、浏览器语言、英文的初始化优先级，继续支持简体中文和英文。已有系统文案随当前语言更新，用户输入、姓名、邮箱和自定义角色名称保持原值。
- **角色表格**：展示名称、描述、系统或自定义类型、权限数量、关联数量和操作入口。完整角色数据支持按名称搜索，以及名称、类型、权限数量和关联数量排序；权限含义和系统角色的只读能力延续现有规则。
- **用户与邀请表格**：同一用户管理页分别展示已激活用户和待处理邀请，各自维护查询状态。用户主要列为姓名、邮箱和角色；邀请主要列为姓名、邮箱、角色、邀请邮件语言、到期时间及操作。创建时间也是可排序字段，应有对应可发现的排序入口。表格支持加载、失败、无记录与无匹配结果状态。
- **邀请范围**：待处理邀请沿用现有接口返回的仍存在记录，可包含已过期邀请；接受或撤销后的历史记录不在该列表中。不能从现有数据推导已接受、已撤销或邮件实际投递成功的历史状态。
- **表单交互**：创建角色、编辑角色、邀请用户和用户角色分配统一弹窗化。角色权限按资源分组，选择控件与错误保持可访问关联；列表行通过明确操作打开表单。保存成功关闭并刷新相应列表，失败在弹窗内显示错误并保留输入。
- **关闭与重置**：关闭按钮、Escape 和遮罩关闭只隐藏弹窗，不清除草稿，也不要求确认放弃。提供明确的主动重置操作；关闭和重置的文案应能区分。关闭后用户可通过顶栏的独立按钮修改偏好，再打开表单继续填写。
- **邀请邮件语言**：使用词汇表中的 Invitation language，独立于操作者的界面语言。新建邀请草稿时按当时界面语言初始化，之后单独选择；恢复已有草稿不重新初始化。提交使用草稿中的语言，重发继续沿用邀请保存的语言。
- **草稿职责**：Zustand 仅管理客户端业务草稿及其操作状态；既有 TanStack Query 继续负责服务端数据、请求与查询缓存。不将列表缓存复制进草稿存储作为另一份事实来源。
- **草稿粒度**：当前操作者有独立的新角色草稿和新邀请草稿；角色编辑与用户角色分配按目标记录标识区分。草稿保存输入、选项、与语言无关的校验信息，以及编辑开始时的服务端基线。后台查询更新不能无条件重新初始化已有草稿。
- **草稿生命周期**：使用内存存储，不启用跨刷新持久化。关闭弹窗和应用内路由切换保留；刷新或页面运行结束后消失。成功提交和主动重置只清除对应草稿。确认退出成功、会话失效或操作者身份变化时清除全部该账号草稿及旧账号的访问管理缓存；退出失败或临时依赖错误不清空。
- **提交生命周期**：允许提交中关闭弹窗，原请求继续，重新打开反映同一提交状态并阻止重复提交。迟到的回调必须匹配其操作者、目标和提交的草稿实例，仅清理本次操作的状态；不能清除后来建立的新草稿。语言变化不重复执行操作。
- **查询范围**：用户和邀请各自按姓名或邮箱做全局包含搜索，去首尾空白、沿用现有文本标准化规则并忽略大小写。百分号、下划线和转义符按普通输入字符处理；空搜索返回全部可见记录。
- **排序与分页**：用户支持姓名、邮箱、创建时间升降序；邀请额外支持到期时间升降序。用户和邀请默认按创建时间倒序。保留前后翻页、默认 25 条与最大 100 条的接口限制；改变搜索或排序回到第一页。角色查询基于已返回的完整角色集合，用户与邀请在服务器上查询。
- **列表 API 契约**：用户与邀请读取接口统一表达搜索词、排序列、方向、游标和页大小，配套调整前端 API 客户端、查询缓存键、HTTP 参数校验、应用服务和数据访问。返回记录和下一页游标，继续沿用既有权限校验和错误协议。
- **稳定游标**：现有只含 UUID 的游标需扩展为包含实际排序边界值、记录 ID、查询与排序上下文的版本化不透明游标。排序字段使用允许列表，查询值参数化；拒绝非法游标以及与当前查询不匹配的游标。时间边界保留后端精度，不经前端格式化后重建。
- **数据库查询顺序**：过滤与排序先于分页执行；排序值相同时使用记录 ID 确定次序，外层角色关联后保持相同实体顺序。以游标保存的边界值翻页，不依赖边界记录继续存在。稳定翻页针对未变化的数据，不承诺跨多次请求的数据快照。
- **数据库结构**：当前字段足以完成主题、草稿、查询和版本校验需求，无需为偏好或草稿增加账号字段。性能索引根据实际查询验证决定；如确需新增，使用正常迁移流程并同步项目数据库版本约束，不直接修改已应用的历史迁移。
- **已有乐观锁**：角色编辑提交 `revision`，用户角色分配提交 `authVersion`；后端在事务内保证版本比较与写入原子性。角色更新会递增版本，用户角色分配变化会递增授权版本。已有过期版本响应为 HTTP 409、`stale_revision`，本轮沿用这一机制。
- **版本与草稿绑定**：草稿始终携带开始编辑时的原版本。不能在保留旧输入的同时，将后台查询到的新版本写进草稿再自动提交。角色权限变化可能提升关联用户的授权版本，即使其角色列表没有变化，也应遵守该校验。
- **冲突恢复**：提交遇到过期版本时保留草稿并显示当前语言的冲突提示，不自动重试、不覆盖服务端结果。重开时发现更新版本也不能静默替换草稿。用户明确选择“放弃草稿并重新载入”后，才将最新输入和版本一起作为新基线；重新加载失败时保留原草稿。
- **对象及权限变化**：目标已删除、选中的角色失效或操作者失去管理权限时，不得继续按失效数据提交；保留可解释的反馈，不将失效选项静默移除后提交另一组权限。现有只读权限、系统角色保护、角色占用及最后一名超级管理员等业务规则继续有效。
- **可访问性与布局**：弹窗有标题、合理初始焦点和关闭后的焦点恢复；菜单与表格操作可用键盘完成。窄屏下主要内容可读、表单可滚动且主要按钮可达，必要的表格横向滚动限制在表格容器内。明暗模式中的文字、边界与焦点状态都需可辨识。

## Testing Decisions

- **质量标准**：测试用户能观察到的行为、公开 API 结果及数据库中的最终业务结果。不要以 Zustand 内部结构、组件渲染次数、翻译函数调用次数或大段快照代替功能验证。
- **最高层边界**：优先复用现有 Playwright 管理端流程，从真实页面操作独立的外观与语言按钮、账户菜单、表格和弹窗，覆盖主题、语言、退出登录、搜索排序、草稿恢复及提交。用实际可访问名称查找控件，不为测试增加生产状态暴露接口。
- **页面集成边界**：复用现有 Testing Library、user-event、真实翻译资源、独立查询客户端和受控 API 响应。请求延迟、退出失败、版本冲突、服务端字段错误及迟到回调等难以稳定触发的情形在这一边界验证。
- **后端集成边界**：复用现有 HTTP 与 PostgreSQL 集成测试。通过真实用户、角色和邀请数据验证全局查询与原子版本校验，不以模拟的 409 证明数据库能够拒绝并发旧写入。
- **既有先例**：已有主题之外的语言持久化测试、认证表单错误随语言变化测试、用户与角色只读权限测试、模拟版本冲突后重新加载测试，以及数据库成功更新和版本递增测试。这些构成复用基础，不新建平行的测试体系。
- **本次入口增补验证**：沿用已确定的浏览器与页面集成测试边界，更新既有控件定位。验证菜单关闭时两个入口分别可见；点击后直接打开各自的选项；外观选择不改变语言，语言选择不改变外观；关闭菜单后焦点回到对应按钮。检查认证页面框架与 Dashboard 全局顶栏，确认头像菜单不再承载偏好入口且退出登录仍可用。通过实际浏览器检查桌面、窄屏及中英文下的布局。本次不新增后端测试边界。
- **主题验证**：浏览器模拟系统明暗变化，覆盖初次跟随系统、显式覆盖、刷新恢复、同源标签页同步及存储不可用时当前页仍可切换。检查认证页、页面框架、表格、弹窗和反馈在明暗模式下的一致性。
- **语言验证**：延续已有“输入与错误保留、提示随语言更新、请求不重复”约束。覆盖关闭业务弹窗后切换语言，再恢复草稿，以及请求开始和结束时语言不同的情形。
- **草稿验证**：四类表单均验证关闭重开、应用内切页恢复、目标隔离、提交成功清理、失败保留、主动重置和刷新清空。用输入值、选择、提示与实际提交参数观察结果。
- **账号与异步验证**：验证退出成功、会话失效、身份切换会清理旧草稿和缓存，退出失败或暂时网络错误不会清理。提交中关闭重开不得多发请求；迟到结果不能清理其他目标、新草稿或另一账号的状态。
- **搜索排序验证**：创建超过一页的数据，确认可以命中第一页以外的记录；覆盖大小写、空白、中文和特殊搜索字符。检查允许排序列、升降序、相同值连续翻页、查询变更回到第一页、两个列表状态隔离、非法排序及游标拒绝。
- **分页边界验证**：覆盖删除游标边界记录后继续翻页，以及带有多个角色的用户／邀请仍正确聚合。对未发生排序字段变化的数据验证无重复或遗漏，不把动态数据变化误判为快照保证。
- **乐观锁验证缺口**：已有数据库测试主要覆盖成功更新和版本递增，前端已有模拟冲突恢复测试；尚未找到数据库层旧版本拒绝及相同版本并发提交断言。本轮补充角色编辑和用户角色分配的针对性集成测试，检查失败响应和最终保存值。
- **乐观锁场景**：两个客户端从同一版本开始，第一份有效修改提交后，另一份不同的旧版本修改必须被拒绝。再通过真实并发验证只允许合法的版本推进；明确重新加载后才可用新版本再次编辑。
- **视觉与可访问性验证**：复用已有浏览器与 axe 检查，补充键盘打开、提交、关闭、菜单子项和焦点恢复检查；在代表性的桌面与窄屏尺寸检查表格、长名称、错误文本、弹窗滚动和明暗主题。
- **范围控制**：按具体风险补充测试，复用已有测试入口。低影响样式修改无需逐项新增断言；不把所有页面、语言、主题和错误做无意义的全组合。
- **执行工作流**：实现阶段遵循本地修改、单向同步到 Centaurus、在 Centaurus 运行验证的约定。需要浏览器验证时转发服务端口并提供本地 URL；不自动在 Codex 侧栏打开预览。本次已执行页面集成测试、类型检查、构建、远端验证和浏览器检查。

## Out of Scope

- 为浏览器主题和界面语言提供账号跨设备同步，或新建通用设置页面、偏好设置弹窗。
- 修改密码、账号安全设置及其他未来账号功能。
- 扩展现有语言集合，翻译用户输入或改变邮件、角色等业务数据的含义。
- 跨刷新、浏览器重启、跨标签页或跨设备恢复业务草稿；草稿历史、多版本草稿与自动保存到服务器。
- 字段级自动合并、强制覆盖他人修改、协同编辑、长时间占用记录的编辑锁或新的通用锁服务。
- 改写现有权限模型、增加新的权限或角色类型、改变系统角色和邀请授权规则。
- 邀请历史、邮件投递状态追踪、批量邀请、批量用户操作或导入导出。
- 用户与邀请的任意页跳转、准确总页数，以及按多值角色列排序；“全局搜索”不扩展为搜索所有显示列。
- 引入独立搜索服务、为未提出的规模目标预设索引集合，或未经验证地调整数据库结构。

- 搜索字段、可排序列、默认次序、现有分页限制和复用测试边界由代码核查与已确认的全局查询需求具体化。它们是本规格的实现边界，不表述为用户逐一指定了内部参数或测试工具。

- Zustand 的独立存储可承载组件之外的草稿状态；跨刷新持久化是另一项能力，本规格明确采用内存生命周期。主题的浏览器保存方式可以参考现有 shadcn Vite 指引。[Zustand 官方文档](https://zustand.docs.pmnd.rs/reference/apis/create-store)、[shadcn 官方文档](https://ui.shadcn.com/docs/dark-mode/vite)
