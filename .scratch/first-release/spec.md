# Temvia 0.1.0 首次公开发布

Status: claimed
Labels: ready-for-agent
Implementation: accepted
Release: not-published

## Problem Statement

Temvia 已具备通用后台模板的基础能力，但当前使用入口仍依赖下载源码并构建生成器，包配置尚不可公开发布，首次使用说明、许可与发布流程也未完成收尾。陌生开发者需要不依赖作者口头指导，就能获取模板、生成独立项目并完成首次登录，同时清楚了解维护责任和验证范围。

## Solution

发布 Temvia 0.1.0：GitHub 提供公开源码、文档和版本说明，npm 注册表分发生成器，使用者通过 pnpm create 创建项目。以 Docker Compose 作为快速开始主路径，提供完整中英文配置、启动和部署说明，另提供开发指南。

本轮冻结功能，只修复已有问题并补齐发布必需配置、文档和验证。生成器与模板自有代码使用 MIT 许可，生成项目由使用者独立维护。通过维护者主动触发的 GitHub Actions 发布，完成发布前实际产物验收及发布后公开入口验证。

## User Stories

1. As a 陌生开发者, I want 在 GitHub 了解模板用途和已有能力, so that 我能判断是否适合自己的项目。
2. As a 陌生开发者, I want 直接通过 pnpm create 获取生成器, so that 我不必先克隆和编译 Temvia。
3. As a 陌生开发者, I want 文档给出完整且经过验证的生成命令与参数, so that 我能创建正确命名的项目。
4. As a 使用者, I want 获得独立的项目源码, so that 我能自行修改和删除其中的功能。
5. As a 使用者, I want 生成项目不依赖 Temvia 运行服务, so that 我能独立部署和维护应用。
6. As a 使用者, I want 生成器正确替换 Go 模块名称, so that 后端能在我的项目中构建。
7. As a 使用者, I want 发布包包含启动项目所需的模板资产, so that 安装后不会出现文件缺失。
8. As a 使用者, I want 生成结果不包含开发数据、秘密或临时文件, so that 获得的是可配置的干净项目。
9. As a 新用户, I want 快速开始明确列出前置工具和版本要求, so that 我能先准备正确环境。
10. As a 新用户, I want 使用 Docker Compose 启动完整系统, so that 首次体验有一条明确主路径。
11. As a 新用户, I want 环境变量和密钥说明数量、名称与代码一致, so that 不会因遗漏配置而启动失败。
12. As a 新用户, I want 知道如何执行数据库迁移, so that 首次启动时数据库处于正确状态。
13. As a 新用户, I want 知道如何找到初始化链接并创建管理员, so that 我能完成首次设置。
14. As a 新用户, I want 按说明完成首次登录, so that 我能实际进入生成的管理后台。
15. As a 开发者, I want 独立于快速开始的开发说明, so that 我能启动开发服务并修改业务代码。
16. As a 部署者, I want 清晰的生产配置和部署说明, so that 我能理解开发环境与部署环境的差异。
17. As a 中文读者, I want 完整的中文快速开始、配置和部署说明, so that 我不必跨语言拼接关键步骤。
18. As an English reader, I want complete English setup, configuration, and deployment instructions, so that I can use the template independently.
19. As a 文档读者, I want 默认英文入口提供明显的中文切换链接, so that 我能找到适合自己的文档。
20. As a 使用者, I want 知道目前只在 macOS 验证过完整首次使用流程, so that 我不会把其他环境的兼容性当成已验证承诺。
21. As a Linux 或 WSL2 使用者, I want 看见这些环境尚未完整验证的说明, so that 我能正确理解使用边界。
22. As a 商业项目开发者, I want 明确允许商业与闭源使用的许可, so that 我能评估和采用模板。
23. As a 再分发者, I want 项目保留必要的版权、许可和第三方声明, so that 我能继续保留这些声明。
24. As a 使用者, I want 知道生成项目不会自动升级, so that 我能自行安排依赖与源码维护。
25. As a 使用者, I want 通过版本记录和重要修复指引了解变化, so that 我能判断如何合并适用于自己项目的修复。
26. As a 使用者, I want 从 GitHub Issues 报告缺陷和建议, so that 反馈有明确入口。
27. As a 安全问题报告者, I want 私密报告入口, so that 我不必公开尚未修复的漏洞细节。
28. As a 使用者, I want 知道维护不承诺固定响应时间或旧版本长期支持, so that 我能建立合理预期。
29. As a 维护者, I want 首版版本统一为 0.1.0, so that 发布包和版本说明对应同一交付。
30. As a 维护者, I want 主动触发 GitHub Actions 发布, so that 普通代码推送不会意外发版。
31. As a 维护者, I want 必要检查失败时阻止发布, so that 未通过验收的版本不会进入公开分发。
32. As a 维护者, I want 从真实打包产物完成首次启动验收, so that 验证结果覆盖使用者拿到的内容。
33. As a 维护者, I want 发布后通过公开命令再次验证生成, so that 能确认真实分发入口可用。
34. As a 维护者, I want 新功能需求留到后续版本, so that 首版能够按既定范围完成。

## Implementation Decisions

- 发布对象为 create-temvia 生成器及随包分发的模板；首版版本为 0.1.0。调整当前禁止发布的包配置，并补齐仓库、许可和问题反馈等发布元数据。
- GitHub 承载公开源码和文档，npm 注册表承载生成器，文档主入口采用 pnpm create temvia@latest，并提供现有 CLI 所需的完整参数。不新增生成器功能，不擅自改名。
- 实施前核实 npm 名称可用性、GitHub 可见性、发布身份及权限；若事实导致既定分发方案必须改变，再请求决策，不将尚未核实的事项写为完成。
- GitHub Actions 由维护者主动触发版本发布，普通推送不发布；必要检查未通过不得进入发布步骤。具体触发机制与身份认证配置在实施时按平台能力选择，不预设已经具备账号权限。
- 包版本、发布说明及对应源码版本应一致；明确区分发布前验收与发布后公开入口验证，不能把后一项声称为发布前已完成。
- 优先修正和扩展已有生成、打包及文档模块。现有打包测试中禁止公开发布的断言，以及严格文件清单，需随许可和双语文档等交付变化同步调整。
- 快速开始以 Docker Compose 为唯一主路线，覆盖前置条件、生成、配置、迁移、启动、初始化和登录；开发指南另述开发服务使用方法。修正密钥数量与实际配置不一致等已发现文档问题。
- 根文档默认英文并链接中文。快速开始、配置与部署内容完整提供中英文，生成项目也需得到对应使用说明；代码注释和内部讨论无需全部翻译。
- 生成器与模板自有代码采用 MIT，保留版权、许可及第三方声明；不得通过给生成项目添加声明而声称拥有使用者新增代码的版权。
- 文档明确完整首次使用流程目前仅在 macOS 测试过。Linux 与 WSL2 标为未经完整验证，不把 Centaurus 上的组件、集成或浏览器测试等同于 Linux 从零安装验证。是否可标记通过须以实际证据为准。
- 生成项目保持独立源码副本，无自动升级承诺；维护者提供版本记录和重要修复指引，使用者自行评估与合并。
- GitHub Issues 为公开反馈入口，安全问题提供可用的私密入口。维护尽力而为，不承诺固定响应时间或旧版本长期支持。
- 不改变业务 API、数据库结构、权限模型、会话行为或产品能力；若验收发现已有缺陷，只做本次发布所需修复。

## Testing Decisions

- 用户已在 Q13 确认测试边界：真实发布产物生成、macOS 按文档首次使用、现有自动化检查、发布门禁及公开命令验证。本规格沿用该确认，不另开采访。
- 最高层主验收边界为“使用者拿到实际打包产物后，在全新目录生成项目并完成首次登录”。验证可观察结果，不用函数调用、工作流文本存在或源码模板测试代替交付验收。
- 复用既有 tarball 打包、离线安装、映射 bin 调用、模块替换和资产检查测试。保留运行时无需开发依赖、模板污染排除、生成 Git 行为等原有保障，按实际新增交付文件更新清单。
- 在 macOS 的全新生成目录按文档执行配置、迁移、启动与首次登录，不复用已有开发数据库或预初始化账号作为首次使用证据。分别核对中英文步骤与实际操作的一致性。
- 运行现有根项目检查、CLI、Git 和打包测试，以及 API 与前端的适用检查。已有业务浏览器测试优先复用；修复导致的回归补在对应现有测试边界，不为发布另建重复业务测试体系。
- 检查实际包及生成结果不包含真实环境变量、凭据、开发数据、依赖安装目录、临时文件或本地工具状态；示例配置应可交付且不含真实秘密。
- 验证发布门禁的外部效果：必要检查失败时没有发布执行，普通推送没有发布，主动触发只发布指定源码对应的版本。凭据不可输出到日志或打包内容。
- 发布前准备发布后验证步骤；实际公开发布后，在模板源码以外的全新目录通过 pnpm create temvia@latest 验证获取与生成，并核对首版版本和必要文件。下载缓存或本地 tarball 不得替代公开入口验证。
- 记录每项验证所用环境与结果。外部权限或环境阻塞时如实列为未完成，不以既有局部通过记录替代。
- 遵守现有执行约束：代码与 Git 操作在本地，开发验证按项目 Centaurus 工作流进行；macOS 完整启动验收是单独门槛，不能由远端测试替代。若需要资源密集的本地执行或与现有环境规则冲突，实施时明确处理，不默默绕过。

## Out of Scope

- 新业务功能，包括文件上传、多租户、支付、通知、工作流及导出。
- 自动升级或同步已经生成的项目。
- 首版之外的功能规划与 1.0.0 稳定性承诺。
- 原生 Windows PowerShell 全流程支持，以及未经执行的 Linux、WSL2 完整兼容性承诺。
- 新建发布展示网站、教程平台或翻译全部内部记录及代码注释。
- 固定支持响应时间、旧版本长期维护或替使用者维护其生成项目。
- 本次规格编写不执行包发布、版本标签推送、GitHub 配置变更或发布实施。
