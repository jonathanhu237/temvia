# 操作日志讨论

Status: resolved

## 最终收敛

本节优先于下方保留的讨论历史。设计讨论完成，尚未开始应用代码实现；按项目 grill-with-docs 约定，等待用户在讨论完成后明确要求实施。

### 记录模型和范围

- 每次纳入范围的操作结束后生成一条结果日志，成功、失败都记录。不记录单独的发起事件，不做双事件关联、处理中状态或严格/异步模式开关。
- 覆盖已有管理操作及账号活动，并提供统一接入入口，后续新操作复用存储和查询能力。不引入 zap 或外部审计服务。
- 记录操作人、发生时间、动作、对象、结果，以及有意义且安全的变更前后值。密码、令牌、邮件密钥仅记录已修改，不保留明文或密文。
- 未验证的登录尝试显示未验证身份，在详情记录尝试账号和来源 IP，不能归因给对应真实用户。普通无效网址等请求不纳入操作日志。
- 邀请创建及重发的成功表示业务操作成功且已提交发送队列，不表示邮件已送达；第一版不为每次后台自动发送重试添加操作日志。

### 保存失败

- 操作结束后统一尝试向 PostgreSQL 保存一条结果日志，写入设置短超时。保存独立于已完成业务，不回滚或改写真实业务结果。
- 写入失败输出不含敏感内容的 API 运行错误并累计失败次数；第一版不增加异步队列或自动重试。异常和进程崩溃时可能缺少历史记录，不承诺补回。
- Compose 部署用 docker compose logs api 查看 API 运行日志；直接启动时在启动终端查看。

### 状态接口和首页提醒

- 提供操作日志记录状态接口，供有日志查看权限的用户在首页看到异常提醒；该接口不代表整个后端健康或历史完整。
- 前端进入首页查询，页面可见时建议每 30 秒刷新。接口查询失败表示状态无法获取，不能冒充正常或断定日志写入失败。
- 用户确认第一版状态存在 API 内存，按单 API 实例设计；重启丢失状态，显示尚无写入结果，待下一次写入更新。多实例共享状态不在本轮。
- 后续写入成功后显示记录已恢复、此前部分记录可能缺失；距最近故障满 24 小时后自动消除恢复提醒，不提供手动处理按钮。持续故障不因时间经过自动变为正常；重启遵守内存状态丢失规则。
- 无需额外部署持续监控服务；本轮不发送邮件等外部主动通知。

### 权限、查询和保留

- 独立操作日志查看权限，默认仅超级管理员拥有，可通过自定义角色授予。拥有权限可看所有模块历史和安全详情。
- 后台提供筛选、分页和详情，不提供编辑、手动删除、导出或实时刷新日志列表。首页状态轮询与列表实时刷新是不同功能。
- 系统设置增加保留天数，默认 180，支持 1～3650 的整数，无永久保留和停止记录选项。
- 沿用系统设置查看/修改权限；操作日志查看权限本身不授予设置修改能力。
- 定期自动清理超期记录；缩短期限会在下次清理删除超期历史，保存时提示这个影响；延长期限不会恢复已删除历史。

## 历史讨论（以最终收敛为准）

## 已确认

- Q1：管理操作与账号活动一起纳入操作日志；未来新增操作也应能接入。
- Q2：增加独立的操作日志查看权限。
- 不引入 zap 来实现本次操作日志功能。
- 最新确认：一次操作只记录一条结果日志。此前讨论的发起/结果双事件方案已被替换。
- 最新补充确认：操作结束后记录结果，成功和失败都各按一次操作生成一条日志；不是同一次操作同时写成功与失败两条。
- 最新 Q1 已确认：日志保存失败不改变业务结果，输出运行错误并累计失败次数；第一版不加队列或重试。替换早先严格策略讨论。
- 最新 Q2 已确认：默认只有超级管理员拥有查看权限，可通过角色授予；有权限即可查看全部模块的日志。
- 最新 Q3 已确认：记录操作对象和有意义的变更前后值；密码、令牌、邮件密钥只记录“已修改”。
- 最新 Q4 已确认：默认保留 180 天，改为在后台手动设置保留期限；到期自动清理，提供筛选、分页和详情，不提供编辑、删除、导出或实时刷新。天数语义、调整后的历史清理和设置权限待细化。
- 保留设置已确认：按天数输入，默认 180；缩短期限后下次自动清理删除超期历史，保存时提示影响；延长不恢复已删除历史。沿用系统设置权限，日志查看权限不授予设置修改能力。
- 故障提醒已确认：后台首页向有操作日志查看权限的人展示记录异常提醒；通过后端操作日志记录状态接口查询。接口反映已观察到的写入故障，不代表整个后端健康或历史完整。无外部主动通知。
- 建议的前端刷新方式：进入首页查询、页面可见时每 30 秒刷新；用户认可状态接口方案，具体轮询间隔作为实现建议。
- 术语：Operation log / 操作日志，区别于 API 请求日志和首页当前运行提醒。

## 代码事实

- 管理操作包括角色创建/编辑/删除、用户角色分配、邀请创建/重发或续期/撤销、邮件设置保存及测试邮件。
- 账号活动包括初始化、登录/退出、密码重置请求/完成、接受邀请。
- PostgreSQL 保存业务数据，Redis 保存登录会话；二者不共享数据库事务。
- 邀请发送通过事务 outbox 排队，排队成功不等于邮件送达。
- 当前无持久化操作日志基础设施；运行日志使用标准 log。

## 调研后的建议（尚未逐项确认）

- 共用操作日志模块、PostgreSQL 存储和显式业务记录入口，未来动作复用查询能力。
- PostgreSQL 管理变更与成功日志一起提交；账号活动记录故障不阻断正常使用，需报告故障。
- 参考：Keycloak 事件分类；Spatie Activitylog 的操作人、对象和变更详情；WorkOS 的统一动作模型。
- 记录故障没有统一策略：OWASP 建议一般日志故障不阻止应用运行，Kubernetes 提供严格拒绝请求的审计模式。

- 来源：https://spatie.be/docs/laravel-activitylog/v5/introduction
- 来源：https://workos.com/docs/audit-logs
- 来源：https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html

## 实际后台源码调研（2026-09-08，优先于前面的历史建议）

- RuoYi-Vue master：LogAspect 在正常返回/抛出异常后构建结果记录，交给 AsyncManager；AsyncFactory.recordOper 在后台任务中插入数据库。日志构建/提交异常在切面捕获，后台写入与原业务不共享事务。结论：后台异步保存，不以成功落库作为原操作成功的前提。
  - https://raw.githubusercontent.com/yangzongzhuan/RuoYi-Vue/master/ruoyi-framework/src/main/java/com/ruoyi/framework/aspectj/LogAspect.java
  - https://raw.githubusercontent.com/yangzongzhuan/RuoYi-Vue/master/ruoyi-framework/src/main/java/com/ruoyi/framework/manager/factory/AsyncFactory.java
- gin-vue-admin main：OperationRecord 在 c.Next() 后收集状态/耗时/错误，再直接 GORM Create。失败时用 zap 输出运行错误，不改写业务结果。操作日志落库并非由 zap 完成。
  - https://raw.githubusercontent.com/flipped-aurora/gin-vue-admin/main/server/middleware/operation.go
- django-auditlog master：模型信号同步调用 log_create；_create_log_entry 在通知 post_log 后重新抛出记录异常。是否导致业务回滚取决于调用方事务边界，不能概括为所有操作自动回滚。
  - https://raw.githubusercontent.com/jazzband/django-auditlog/master/auditlog/receivers.py
- 这些是源码样本，不是全行业统计；普通后台操作记录与模型变更审计库的默认策略存在差异。
- 当前推荐（待确认）：采用一条结果日志和统一入口；业务完成后在独立写入中短超时尝试保存，失败输出安全运行错误和失败计数，不改变业务结果。第一版不引入异步队列、严格模式或双事件。接受进程崩溃或存储故障时可能缺记录。
