# Graceful shutdown

Status: ready-for-agent

## Problem Statement

应用重启或停止时，当前主程序没有等待 HTTP 排空完成，只等待邮件派送；后台清理没有统一等待，固定 HTTP 超时、邮件租约和容器停止宽限也没有统一约束。用户正在保存的数据和邮件结果可能因为进程提前退出而中断，部署者无法通过一个配置可靠控制停机等待。

## Solution

停止接收新工作，让在途请求和已领取邮件任务在统一预算内完成，后台清理取消退出。全部完成则提前退出；预算耗尽或再次收到终止信号时结束进程。只维护一个环境配置 SHUTDOWN_TIMEOUT，默认 30s，同时供应用和 Compose 使用，总预算包含退出预留时间。

## User Stories

1. As a 部署者, I want 默认有界优雅停机, so that 正常重启不会立刻打断在途工作。
2. As a 部署者, I want 在 .env 中仅配置 SHUTDOWN_TIMEOUT, so that 不必同步维护两个相关时间值。
3. As a 部署者, I want 应用和 Compose 使用同一个配置, so that 容器配置与应用预算一致。
4. As a 部署者, I want 非法或非正预算启动时报错, so that 配置错误不会静默生效。
5. As a 用户, I want 已开始的 HTTP 请求继续处理并返回响应, so that 保存操作有机会正常完成。
6. As a 部署者, I want 停机后停止接受新 HTTP 请求, so that 工作量能够收敛。
7. As a 用户, I want 已领取邮件尽力发送并记录结果, so that 重启尽量不打断通知。
8. As a 部署者, I want 停机后不再领取邮件任务, so that 不必清空队列才能停机。
9. As a 用户, I want 在途请求新创建的邮件任务保存在队列中, so that 重启后仍可发送。
10. As a 部署者, I want 后台清理取消并退出, so that 无须等待非必要维护完成。
11. As a 用户, I want 在途工作完成前数据库保持可用, so that 停机不会主动破坏事务收尾。
12. As a 部署者, I want 多类工作并行排空且共享截止时间, so that 各阶段不会累计多个预算。
13. As a 部署者, I want 工作提前完成即退出, so that 不必每次等满预算。
14. As a 部署者, I want 总预算内预留取消关闭时间, so that 应用不会等到容器强杀时才开始退出。
15. As a 部署者, I want 超时取消剩余工作并强制关闭 HTTP 连接, so that 不会无限等待。
16. As a 部署者, I want 超时或异常退出记录原因并返回非零状态, so that 能区分成功停机和未完成收尾。
17. As a 部署者, I want 第二次终止信号立即终止进程, so that 可以主动跳过等待。
18. As a 部署者, I want 非容器部署也能通过环境变量控制预算, so that 不依赖 Compose 才能正确停机。
19. As a 维护者, I want 生成项目包含配置、实现和说明, so that 模板交付保持完整。

## Implementation Decisions

- 首次 SIGINT 或 SIGTERM 启动统一停机流程；第二次终止信号立即终止。
- SHUTDOWN_TIMEOUT 默认 30s，接受正的 Go duration；配置示例、应用配置、Compose 环境传递和 stop_grace_period 使用同一项，不引入第二个用户配置或计算时间的启动脚本。
- 总预算从首次信号开始，包括业务排空和退出预留。默认业务排空最多 28s，末尾 2s 留给取消、资源关闭和进程退出。较短预算的预留按比例缩小；具体安全计算作为实现细节记录并测试，不增加配置。不可因极短正值出现负数或溢出。
- 停止接收新 HTTP 请求；已有请求继续处理事务、创建 outbox 任务和返回响应。停机不主动清空邮件队列。
- 邮件停止领取新任务；已领取任务继续发送及记录结果，但必须受共同停机截止约束，不可通过脱离取消或阶段性新建租约超时逃逸总预算。
- 现有任务自身更短的超时继续生效。HTTP、活动邮件和后台任务的等待不串行累计预算。
- 操作历史清理及会话、限流状态清理收到取消并等待退出；不改变这些任务的业务规则。
- 正常收尾时先等待工作结束，再关闭数据库等依赖；提前完成立即退出。
- 排空截止后取消剩余工作、强制关闭 HTTP 连接；退出和资源关闭不得无限阻塞。超时或异常记录原因并非零退出，正常完成返回零。
- 异常服务结束也应有有界清理，避免直接致命日志跳过清理。
- 保持现有邮件租约、重试和条件确认语义。强制中断可能导致 HTTP 结果不明或邮件重发，不承诺所有工作完成或邮件恰好发送一次。
- 同步生成器文件清单和文档（如新增文件需要），不修改历史移除 Redis 规格，不向领域词汇表添加生命周期实现细节。

## Testing Decisions

- 测试边界已经用户确认：以服务进程和真实 HTTP 连接为主，复用邮件 dispatcher、配置及生成器现有测试。
- 仅验证公开行为和可观察结果，不断言私有辅助函数调用次数或具体内部组织。
- 服务生命周期测试使用真实监听连接与受控在途工作，验证不提前退出、停止新请求、完成后提前退出、共同预算及依赖在收尾时可用。
- 子进程测试验证真实终止信号、正常与超时退出码、第二次信号立即终止，以及不响应取消的工作不能阻止有界退出。
- 复用邮件派送现有排空测试，覆盖停止领取、活动邮件发送和结果记录、截止取消以及剩余队列重启可处理。
- 验证后台清理取消及退出等待，多个工作不能分别耗尽完整预算。
- 配置测试覆盖默认值、覆盖、非法和非正 duration、短预算的安全预留；生成器和 Compose 回归覆盖配置显式传递与同源值。
- 优先受控同步和合理时间容差，避免靠脆弱 sleep 排列并发。
- 运行局部测试及适用完整测试套件，记录环境限制，不将未执行测试写为通过。

## Out of Scope

- 任何限流算法、维度、额度、可信代理或普通 API 限流改动。
- 新增任务恢复框架、消息队列、分布式调度或多实例交付保证。
- 保证邮件恰好发送一次、HTTP 强制中断后结果一定可知、停机前清空 outbox。
- 零停机发布、流量切换编排和外置部署平台自动配置。
- UI、认证会话规则、数据库 schema 或业务功能重构。
