# 生成应用的基本防滥用能力

Status: ready-for-agent
Triage: ready-for-agent

## Problem Statement

Temvia 生成的后台应用需要在没有额外配置网关限流时，也具备基本防滥用能力。当前登录和密码找回请求已有全局与邮箱维度限流，但尚未形成覆盖匿名认证入口、邀请发信与测试邮件的完整策略。单靠严格的全局额度会使一个攻击来源影响其他用户；单靠邮箱额度又可能使攻击者持续针对某个邮箱，妨碍本人登录。

用户希望默认保护密码计算、账号访问及邮件发送，同时避免共享公司公网 IP 的正常用户互相影响。不希望为了基本防护增加 Redis、复杂后台设置、人工解锁流程或全站统一 API 限额。

## Solution

生成应用默认启用分操作、分维度的基本防护：匿名敏感入口具备较宽松的来源限流，登录与邮件等操作另有更精细的对象或操作者限制，资源总量限制只承担兜底职责。不同操作不共用一个日常业务额度；登录不会因为密码找回额度耗尽而被直接禁止。

短时限制自动恢复，不对账号设置长期或永久锁定。真实超限返回请求过于频繁；无法检查限流状态时暂停受保护的敏感操作，返回服务暂不可用，不主动清除现有登录会话。

提供开箱即用的默认值、环境变量和部署说明，不增加后台设置页面。入口代理的额外防护作为公网部署建议，而非应用基本防护生效的前提。

## User Stories

1. As a 模板使用者, I want 生成项目默认启用基本防滥用, so that 无需先配置网关才能保护敏感操作。
2. As a 部署者, I want 默认策略适合普通后台使用, so that 不需要自行研究算法才能上线验证。
3. As a 用户, I want 登录尝试受到适当限制, so that 密码猜测和撞库更困难。
4. As a 用户, I want 不同来源针对同一邮箱的尝试也受到约束, so that 仅更换 IP 不能完全绕过防护。
5. As a 用户, I want 同一来源不断更换邮箱仍受限制, so that 防护不只针对单个账号。
6. As a 用户, I want 与同事共享公网 IP 时仍能正常登录, so that 一个同事偶尔输错密码不轻易影响整个公司。
7. As a 用户, I want 密码找回和登录分别计数, so that 请求找回密码不会直接占用登录额度。
8. As a 用户, I want 短时限制自动恢复, so that 无需联系管理员人工解锁。
9. As a 用户, I want 失败尝试不会把账号永久锁住, so that 攻击者不能轻易制造长期账号不可用。
10. As a 用户, I want 额度耗尽后重复请求不无限顺延恢复时间, so that 停止滥用后能在明确的时间规则下恢复。
11. As a 用户, I want 密码找回邮件具有接收对象限制, so that 邮箱不被反复轰炸。
12. As a 用户, I want 密码找回接口不泄露邮箱是否已注册, so that 防滥用不会引入账号枚举。
13. As a 用户, I want 过多找回请求不锁定账号或撤销会话, so that 本人仍可按正常认证规则使用系统。
14. As a 邀请接收者, I want 邀请邮件具有合理的重发间隔, so that 不会收到大量重复邀请。
15. As a 管理员, I want 创建、重发及续期邀请都受邮件防滥用保护, so that 切换操作不能绕过同一接收对象的发送限制。
16. As a 管理员, I want 邮件额度不足时邀请状态和原邀请链接不被修改, so that 被拒绝的操作不会破坏已有邀请。
17. As a 管理员, I want 不同接收人的发送也受操作者额度限制, so that 一个已登录账号不能无限量发信。
18. As a 管理员, I want 测试邮件同样受到限制, so that 测试功能不能成为不限量发信入口。
19. As a 管理员, I want 无权限的人不能消耗我的专属发送额度, so that 限流不会成为越权影响业务的方式。
20. As an 邀请接收者, I want 接受邀请入口具有基本来源防护, so that 大量无效请求不会无约束地消耗服务资源。
21. As a 用户, I want 完成密码重置入口受到基本保护, so that 保护不只停留在发送重置邮件的步骤。
22. As a 初始部署者, I want 首次设置入口也被检查和保护, so that 上线初始化阶段没有遗漏的高成本匿名入口。
23. As a 用户, I want 无效链接仍遵守原有单次使用与有效期规则, so that 新限流不改变账号激活和恢复语义。
24. As a 用户, I want 看到与当前操作匹配的请求过于频繁提示, so that 不会在测试邮件或接受邀请时看到登录错误文案。
25. As a 用户, I want 限流依赖故障被显示为服务暂不可用, so that 不会被误告知是自己操作太频繁。
26. As a 已登录用户, I want 限流检查故障不主动清除登录凭证, so that 恢复后可以按正常会话规则继续使用。
27. As a 管理员, I want 普通后台查询、编辑和会话状态检查不被新增统一额度限制, so that 防护不会干扰正常管理和轮询。
28. As a 部署者, I want 通过环境变量调整安全参数, so that 无需修改代码或进入后台即可适配部署环境。
29. As a 部署者, I want 非法限流配置在启动时被拒绝并说明原因, so that 错误配置不会静默关闭防护。
30. As a 部署者, I want 应用只信任明确配置的代理来源信息, so that 客户端不能伪造请求头绕过 IP 限制。
31. As a 部署者, I want 直连应用时也能识别来源并启用防护, so that 代理不是必要依赖。
32. As a 模板维护者, I want 并发请求不能超发额度, so that 防护在真实并发下仍然可靠。
33. As a 部署者, I want 过期限流状态被自动回收, so that 随机来源和邮箱不会使状态无限累积。
34. As a 管理员, I want 已有操作历史正确区分限流失败和依赖不可用, so that 排查时不会把服务故障当成用户滥用。
35. As a 模板使用者, I want 不新增 Redis 或独立限流服务, so that 基本防护不增加运行基础设施。
36. As a 部署者, I want 文档明确能力边界与公网代理建议, so that 不把应用限流误认为大规模 DDoS 防护。

## Implementation Decisions

### 已确认的产品边界

- 本轮补充现有限流，不是从零重写认证，也不是为所有 API 设置统一额度。
- 覆盖匿名认证入口与发邮件操作；普通后台查询、编辑、退出登录和只读会话检查不新增统一请求限额。
- IP 限制相对宽松，对象与具体操作限制更精细；不同操作分别计数。
- 不增加账号长期或永久锁定、管理员解锁或自动强制退出逻辑。受限的是操作额度，不是用户的激活状态、角色或会话有效性。
- 额度不足和限流依赖故障必须区分。依赖故障时敏感操作拒绝执行，不降级为无条件放行。
- 第一版只有默认值与环境变量，不提供后台限流配置、管理接口或新增权限。

### 当前实现与修改范围

- 现有认证应用服务在密码验证前检查登录限流；邮箱已规范化，登录成功后重置邮箱桶。密码找回请求另有独立限流端口。
- PostgreSQL 适配层已有全局及邮箱令牌桶、短事务原子扣减、数据库时间、操作超时和分批清理。沿用这些机制扩展必要的维度和命名空间，不重新引入 Redis，也不建立面向任意业务的通用配额平台。
- 扩展现有 HTTP 适配层、认证与访问管理应用服务、邮件设置服务、限流端口、PostgreSQL 适配及迁移、依赖装配与配置。端口只增加本轮所需的操作类型及可信来源、操作者或规范化目标信息；不把整个 HTTP 请求传入应用层。
- 现有密码计算已有进程内 Argon2id 并发限制，应保留。来源/操作限流控制频率，哈希并发限制保护同时发生的高成本工作，两者不能互相替代。
- 现有操作历史已具备可信代理来源解析。本轮优先复用并核查该能力，而不是为限流复制一套不同的来源判定。

### 入口覆盖矩阵

| 操作 | 主要维度与要求 |
| --- | --- |
| 登录 | 来源 IP＋规范化邮箱；操作全局额度仅作资源兜底；保留密码计算并发保护 |
| 请求密码找回 | 独立来源 IP、规范化接收邮箱和该操作总量；不存在的邮箱也走一致的额度规则 |
| 完成密码重置 | 独立来源限额，在高成本工作前保护；不得为攻击者任意提交的 token 创建无界状态 |
| 接受邀请 | 独立来源限额，保留邀请链接预检、单次使用及最终事务校验 |
| 完成首次设置 | 独立来源限额，保留设置令牌验证与仅能完成一次的约束 |
| 创建、重发及续期邀请 | 完成权限检查后，按操作者和规范化接收邮箱检查；这些同目的发信共享邀请发送策略，避免切换入口绕过 |
| 测试邮件 | 完成权限检查后，按操作者、接收邮箱和该操作总量检查；在实际发送之前拒绝 |
| 密码变更通知 | 核查由成功密码重置派生的现有路径；通过受保护的上游操作约束触发频率，保留既有 outbox 和通知语义，不把通知丢弃当限流 |
| 设置状态、公开系统名称/图标、当前用户与会话检查 | 审计确认其风险，但本轮不新增严格统一额度；保留既有请求处理与认证规则 |

- 同一邮件目的的多个触发入口共享相应额度；不同邮件目的和登录策略隔离。系统级资源压力仍可能影响多个操作，文档不得承诺绝对隔离。
- 邮件限制控制用户触发的发送请求，在修改邀请、替换链接、创建新 outbox 工作或直接发送前生效。被限流或检查失败不得导致业务部分完成。
- 不在本轮实现 SMTP 供应商每日计费配额、worker 调度节流或投递恰好一次。已有 outbox 重试不重复算作用户新触发的请求，不静默丢弃已接受的通知。
- 管理端权限校验先于操作者及目标专属额度扣减；限流不是授权替代品。匿名来源防护应尽可能在账号查询、密码计算、邮件及其他昂贵副作用前生效。

### 计数、恢复和资源边界

- 使用令牌桶表达容量与补充间隔，保留可接受突发和持续速率的区别。每个适用桶的维度必须明确：IP 桶与邮箱桶分别约束，不可用单一 IP＋邮箱组合桶取代二者。
- 来源尝试计数与业务发送额度区分：已到达的匿名尝试可消耗来源额度；被对象额度拒绝的请求不得继续消耗成功接受操作的全局额度或创建业务副作用。多个业务桶的允许与扣减保持原子性。
- 成功登录只重置应当恢复的邮箱登录桶，不重置来源或全局额度。不要让攻击者通过一个已知有效账号反复成功登录清空来源防护。
- 时间补充自动恢复额度。已超限请求不得仅因继续到达而无限推迟恢复时间；不实现失败次数触发的永久封禁。
- 邮箱级短时限制仍可能被持续分布式攻击反复消耗。本轮降低误伤，不承诺在任意持续攻击下目标账号始终可登录；不要通过未验证身份的白名单或跳过密码检查解决这一问题。
- 保持短事务、确定锁序、原子首次创建和有界数据库等待；禁止在限流事务中执行密码计算或网络发信。
- 来源状态须规范化 IP，不把源端口作为身份；统一 IPv4 与等价映射表示。默认不合并整个 IPv6 网段或公司网络作为同一主体。
- 仅可信直连代理能提供转发来源，从靠近应用的一端解析可信代理链；不可信请求的转发头不能改变限流身份。明确缺失、非法转发头与无法解析远端地址时的保守回退，不因解析失败自动放行。
- 使用现有摘要机制避免不必要的明文邮箱/IP 状态；摘要不应被描述成绝对匿名。状态设置有限保留时间并分批清理，清理延迟不改变额度生效时间，清理竞争不能提前恢复仍受限的桶。
- 新增维度需要前向迁移，不改写无关历史迁移，不删除用户、会话或业务数据。扩大命名空间和桶类型约束时处理现有限流记录，明确配置变更后的额度裁剪与保守过期规则。
- 继续按当前单 API 实例交付，数据库并发正确性为必需；不将多实例集群或跨地域协调作为验收范围。

### 默认值与配置

- 讨论确认了策略和配置方式，未批准具体新阈值。实现者应给出完整的默认策略表与环境变量，说明容量、每次补充量、补充间隔、对应持续速率、维度、计数时机及恢复行为；这些是实现选值，不得标注为用户已确认数字。
- 当前登录全局容量为 10、每 6 秒补 1，邮箱容量为 5、每分钟补 1；密码找回全局容量为 10、每 6 秒补 1，邮箱容量为 3、每 20 分钟补 1。这些是现状，不是本轮全部原样保留的约束。
- 默认值以小型后台为基线：同一公网 IP 下多个正常用户可以短时间登录；单一邮箱的少量错误不耗尽所有用户额度；密码找回或测试邮件的重复点击会被限制。全局登录桶不应比单个来源桶更容易先耗尽，应结合现有哈希并发与数据库连接预算重新评估，不能只随意放大连接池。
- 邮箱默认值优先沿用已有值，只有满足本轮安全与可用性目标确有必要时才调整并解释原因。新阈值通过低额度可控测试验证机制，并用默认配置的共享 IP 场景验证相对关系。
- 现有有效环境变量尽量保留，新增值有安全默认值；如必须改变旧变量语义，必须明确记录，不允许静默忽略。配置统一贯通默认值、校验、示例环境文件、Compose 与生成项目文档。
- 拒绝非正容量、不合法或过短间隔、溢出和非法代理网段等无效配置，不把零值解释为关闭防护。配置为启动时加载，本轮不要求热更新。

### HTTP、前端与操作历史

- 沿用现有问题响应契约：真实额度不足为 429／rate-limited；限流存储故障或超时为 503／dependency-unavailable，不能映射为 401 或清除登录 Cookie。
- 前端按操作提供准确的中英文超限提示；通用提示不得把所有 429 都解释成登录失败。服务暂不可用不触发自动退出。后台不新增标题、设置卡片或无关界面。
- 本轮不强制新增 Retry-After、剩余额度头、精确倒计时或自动重试协议；保留现有 API 形状，避免暴露命中维度、账号存在性或剩余尝试次数。
- 对有效与不存在邮箱采用一致的找回响应和限流规则，不因查询账号存在性选择是否创建或消耗额度。保留现有账号枚举防护，不扩展为重写全部认证侧信道处理。
- 已纳入操作历史的操作继续记录一次结果，限流和依赖故障使用对应错误分类；输入的邮箱不构成已验证操作者身份。不得为重复拒绝新增无限放大的同步日志工作，也不新增每个 API 请求一条操作历史的要求。
- 依赖故障不主动退出用户不代表数据库不可用时普通业务必然可用；普通请求继续遵守自身依赖、认证、会话有效期及撤销规则。

## Testing Decisions

- 以外部可观察行为为验收依据：HTTP 状态与响应、Cookie、真实业务状态、邮件任务或发送结果及时间恢复。避免断言私有函数、具体 SQL 文本或某个内部类型必须存在。
- 主测试边界采用现有 HTTP handler＋真实应用服务＋真实 PostgreSQL 集成测试，复用在线用户 HTTP 集成测试的装配与数据库夹具。通过可控邮件发送替身观察直接发送，不连接真实 SMTP。
- 尽量在该边界覆盖登录、密码找回请求及完成、邀请接受、首次设置、邀请创建/重发/续期和测试邮件。不为本轮新增测试框架或生产测试端点。
- 补充现有 PostgreSQL 端口集成测试，仅处理 HTTP 难以精确控制的首次创建竞争、多桶原子扣减、时间补充、配置变化与清理竞争；复用已有状态集成测试方式，避免长时间 sleep。
- 复用应用层 fake 或依赖包装模拟限流故障，验证没有密码修改、邀请变更、会话创建、新 outbox 或发送副作用；不要让整个数据库断开掩盖限流组件的独立错误映射。
- 覆盖同 IP 多邮箱、同邮箱多 IP、换邮箱攻击、共享 IP 正常登录突发、操作命名空间隔离、正确密码登录不清空 IP 桶、重复拒绝不无限延长恢复时间。
- 验证来源限流在昂贵操作之前生效，邮箱额度拒绝不额外耗尽接受操作的全局桶；保留现有哈希并发限制回归。进行小型受控并发检查，记录热点锁等待与资源观察，不声称未经测试的 QPS。
- 覆盖直连、不可信转发头、可信单层及多层代理、伪造前缀、缺失/非法头、IPv4 等价表示及 IPv6；IP 身份不得随源端口变化。
- 覆盖邀请邮件跨创建/重发入口的同目标约束、操作者跨收件人约束、无权限请求不消耗目标业务额度、测试邮件实际发送前拒绝。受限重发不能使原邀请链接失效，受限密码找回不能替换既有链接。
- 验证已有密码变更通知和 outbox 重试语义不回归，未增加用户动作时不重复扣用户发送额度。
- 验证存在和不存在邮箱的公开响应及计数规则一致，不泄露目标是否存在；首次设置和邀请/重置链接单次使用与有效期保持不变。
- 验证 429 与 503 的差异、已有会话不被清除、限制解除后可重试；不承诺故障期间不相关数据库业务仍可运行。
- 复用现有前端问题映射、认证表单和设置/邀请交互测试，覆盖中英文上下文提示与 503 不触发主动退出，不新增整套浏览器测试设施。
- 配置测试验证默认开启、非法输入拒绝、旧变量兼容和新增参数贯通。生成器与模板基线测试验证新文件/迁移完整进入生成项目，默认 Compose 仍无需 Redis。
- 使用升级后的数据库验证旧数据保留与新约束可用。清理失败或未运行不得使额度提前恢复。
- 测试边界在发布规格时说明，供用户实施前审阅；本次未追加访谈，不将该测试方案描述为已经获得单独确认。

## Out of Scope

- 所有 API 一刀切的严格应用层限流，普通后台查询、编辑或会话轮询的新配额。
- 大规模 DDoS 防护、WAF/网关产品集成、自动配置云厂商策略及攻击下绝对可用性承诺。
- Redis、独立限流服务、通用多租户/API key 配额平台、多实例集群验收。
- CAPTCHA、MFA、设备指纹、IP 信誉、ASN/地域拦截及复杂风控评分。
- 长期或永久账号锁定、人工解锁页面、白名单绕过认证及因超限而强制退出。
- 后台限流配置页面、配置权限、热更新或限流运营仪表盘。
- SMTP 供应商计费配额、精确每日发送上限、重写 outbox、投递恰好一次及丢弃安全通知。
- 新的精确倒计时、自动重试协议或强制新增限流响应头。
- 更换框架、认证目录重构、JWT 改造、会话续期规则调整及无关 UI 改造。
- 新增领域术语或 ADR：本轮沿用现有用户、邀请、邀请链接、密码重置链接和操作历史定义，限流参数属于实现决策，不写入领域词汇表。
