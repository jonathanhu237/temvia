# 用户停用、恢复与删除 — 讨论结论

Status: open

## 产品方向

借鉴 GitLab 的“允许停止访问，也允许删除账号但保留关联记录”方向，不照搬全部机制。用于离职或暂停访问，以及清理测试、重复、误建账号。仅支持逐个操作，不做批量。

## 已确认决策

1. 沿用 users.read / users.write，不新增生命周期专用权限。用户读取用于查看用户和状态，用户写入用于现有角色管理及停用、恢复、删除。
2. 有用户写入权限者可以停用、恢复、删除任意其他用户，包括 Super Admin，不比较双方权限范围。用户已明确接受普通管理员可删除 Super Admin 的后果。
3. 角色授予仍保持现有规则，不因生命周期操作可针对任意用户而开放超范围授权。只有 Super Admin 能授予 Super Admin 角色。
4. 禁止停用或删除本人。停用、删除及角色调整均不能使未停用的 Super Admin 数量降为零。
5. 停用立即使所有既有会话失效，阻止登录及通过密码找回恢复访问；保留账号、姓名、邮箱、密码、角色分配及历史。邮箱仍被占用。
6. 停用用户可由管理员调整角色，仍遵守原有角色授权规则。其角色分配计入角色使用情况，不能因用户停用而删除仍被分配的角色。
7. 恢复允许使用原账号及当前角色重新登录，不恢复旧会话。原密码仍保留。
8. 停用使旧密码重置链接失效，恢复后也不能再次使用旧链接，需要重新申请。
9. 删除不可恢复，不要求先停用。不做软删除回收站或可恢复账号。删除登录凭据、会话、重置权限和角色分配，不把这些当作需保留的业务记录。
10. 删除保留操作历史与关联业务记录，不连带删除用户的历史贡献。保留原姓名、邮箱、原用户标识，并标记“已删除用户”；记录继续遵循既有保留期限。删除账号不等于清除所有个人信息。
11. 删除后邮箱可以重新邀请，新账号使用全新用户身份，不继承原密码、角色、会话或历史归属，不按邮箱将旧历史重新绑定。
12. 创建者被停用或删除不撤销其发出的邀请。邀请按原有效性规则继续使用，由有权限的管理员管理；保留已删除创建者身份快照。
13. 用户列表默认同时展示正常和停用用户，增加状态及状态筛选。已删除用户不出现在用户管理列表，不增加回收站或已删除用户管理页。
14. 正常用户显示停用操作，停用用户显示恢复操作，两者均可直接删除。停用与恢复使用确认框；删除要求输入目标邮箱，明确不可恢复及关联记录保留。
15. 已登录用户被停用时，服务端立即拒绝旧会话；页面检测后提示“账号已停用，请联系管理员”并返回登录页。
16. 未登录的登录和找回密码入口保持统一失败或受理提示，不暴露邮箱是否存在或是否停用。

## 实施前应保留的技术注意事项

以下为探索发现，不是新增产品要求或已选定技术方案：

- 当前账号没有停用状态，认证、会话、密码恢复及在线用户查询需要统一识别有效账号。
- 当前操作历史的 actor_user_id 在账号删除时被设为空，虽然姓名和邮箱快照保留，但新要求还需保留原用户标识并能识别删除状态。不能仅依赖现有外键行为。
- 当前邀请 created_by 外键阻止删除创建者，需要调整关联保存方式；不能用级联删除邀请解决。
- 用户会话、角色、密码重置与用户关联的邮件任务存在级联删除关系。需要检查已领取邮件及并发请求，确保无效链接不能重新获得访问权，不承诺撤回已经交给 SMTP 的邮件。
- 最后一位可用 Super Admin 的保护必须覆盖停用、删除、恢复及角色变更的并发执行，不能只做前端数量判断。
- “已删除用户”的保留身份如何实现尚未限定；不能为保留历史而留下可登录或可恢复的账号。
- 新业务模块需要自行定义必要的归属约束，不建设通用所有权转移平台，不默认级联删除业务数据。
