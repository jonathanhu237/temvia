# 用户停用、恢复与删除

Status: resolved
Triage: ready-for-agent
Progress: implementation and self-tests complete; user accepted and authorized commit/push (see verification.md)

## Problem Statement

当前后台只能查看用户、修改角色及强制退出。强制退出结束已有会话，但用户仍可再次登录，无法满足离职、暂停授权等场景；用户列表也无法清理测试、重复或误建账号。

账号存在与历史记录保留目前没有完整的生命周期边界。直接删除可能受到邀请创建者外键约束，或丢失历史中的原用户标识；把任何历史记录都视为删除障碍，又会使使用过的测试账号几乎无法清理。

管理员需要能够暂停访问、恢复访问或永久移除账号，同时不破坏历史追踪、已发出的邀请和必要的管理安全保障。

## Solution

借鉴“删除账号但保留贡献”的产品方向，提供三个明确区分的逐个用户操作：

- 停用：立即终止所有会话并阻止访问，保留账号、密码、邮箱、角色分配与历史。
- 恢复：重新允许该用户使用保留的账号及当前角色登录，不恢复旧会话或已失效的重置链接。
- 删除：不可恢复地移除账号与访问凭据，释放邮箱，但保留关联历史与业务记录，使用原身份及“已删除用户”标记追溯。

沿用用户读写权限。用户写入允许对任意其他用户执行生命周期操作，包括 Super Admin，不比较双方权限范围；角色授予仍保留原有限制。禁止停用、删除本人，并始终保留至少一位可用 Super Admin。

用户列表显示正常与停用状态，支持筛选和逐个确认操作，不提供批量操作、回收站或已删除用户管理页。

## User Stories

1. As an 管理员, I want 停用离职用户, so that 对方不能继续访问系统而历史仍可追溯。
2. As an 管理员, I want 暂停用户访问但保留其账号, so that 无需重新邀请即可在将来恢复。
3. As an 管理员, I want 停用立即使所有设备会话失效, so that 关闭登录入口之外也能阻止已登录用户继续使用。
4. As an 管理员, I want 恢复已停用用户, so that 对方可以重新使用原账号。
5. As an 恢复后的用户, I want 使用保留的密码重新登录, so that 不必重新激活账号。
6. As an 管理员, I want 恢复不复活旧会话, so that 之前失效的登录不能重新获得访问权。
7. As an 管理员, I want 调整停用用户的角色, so that 可以先准备新的授权再恢复访问。
8. As an 角色管理员, I want 停用用户的角色仍计入使用情况, so that 不会误删仍被分配的角色。
9. As an 管理员, I want 停用用户继续占用邮箱, so that 不会为同一个保留账号创建第二个身份。
10. As an 管理员, I want 删除使用过的测试账号, so that 用户列表不会被无用账号堆积。
11. As an 管理员, I want 正常和停用用户都能直接删除, so that 清理账号无需先走停用流程。
12. As an 管理员, I want 删除移除账号的登录凭据、会话和重置权限, so that 已删除账号不能继续访问。
13. As an 管理员, I want 删除用户不删除其关联记录, so that 清理账号不会破坏历史和业务成果。
14. As an 操作历史查看者, I want 看到已删除用户原来的姓名、邮箱及用户标识, so that 能区分不同人的历史行为。
15. As an 操作历史查看者, I want 明确看到“已删除用户”标记, so that 不会误认为历史身份仍是可管理账号。
16. As an 管理员, I want 删除操作本身进入操作历史, so that 可以追踪谁删除了哪个账号及结果。
17. As an 管理员, I want 停用与恢复操作进入操作历史, so that 访问状态变更能够追溯。
18. As an 管理员, I want 删除后重新邀请相同邮箱, so that 可以重建测试账号或接纳重新加入的人。
19. As an 重新受邀用户, I want 获得全新的用户身份, so that 不会继承原账号权限或会话。
20. As an 操作历史查看者, I want 旧记录不因邮箱复用归属到新账号, so that 历史身份保持准确。
21. As an 受邀用户, I want 创建邀请的管理员停用后邀请仍有效, so that 自己的加入流程不被无关人事变动中断。
22. As an 受邀用户, I want 创建邀请的管理员删除后邀请仍有效, so that 可以按原邀请规则激活账号。
23. As an 邀请管理员, I want 管理已停用或已删除创建者发出的邀请, so that 系统工作不依赖原创建者继续拥有账号。
24. As an 只读管理员, I want 查看用户状态但不能变更状态或删除, so that 现有读写权限边界保持明确。
25. As an 拥有用户写入权限的管理员, I want 对任意其他用户执行生命周期操作, so that 不需要另外获取目标角色范围内的权限。
26. As an Super Admin, I want 生命周期管理仍受最后一位可用管理员保护, so that 系统不会失去最高管理入口。
27. As an 管理员, I want 系统阻止我停用或删除本人, so that 不会通过误操作切断自己的管理入口。
28. As an 管理员, I want 角色授予继续遵守原范围限制, so that 生命周期权限不会隐式变成无限授予权限。
29. As an 管理员, I want 并发停用、删除和角色变更也保持安全保护, so that 两个各自看似合法的操作不会共同锁死系统。
30. As an 管理员, I want 用户列表同时展示正常和停用用户并支持状态筛选, so that 可以查找待管理账号。
31. As an 管理员, I want 按用户当前状态看到停用或恢复操作, so that 可执行动作清晰明确。
32. As an 管理员, I want 停用与恢复前确认目标, so that 降低选错用户的风险。
33. As an 管理员, I want 删除时输入目标邮箱并看到不可恢复提示, so that 清楚操作对象和后果。
34. As an 管理员, I want 操作失败或记录已变更时得到明确反馈, so that 不会把未完成的操作误认为成功。
35. As an 被停用的已登录用户, I want 页面检测失效后说明账号已停用并返回登录页, so that 知道应联系管理员而不是反复登录。
36. As an 系统管理者, I want 匿名登录和找回密码响应不泄露账号状态, so that 外部人员不能探测邮箱是否注册或停用。
37. As an 管理员, I want 停用使旧密码重置链接失效, so that 用户不能借恢复密码绕过停用。
38. As an 恢复后的用户, I want 能重新申请密码重置但不能使用旧失效链接, so that 安全权限不会意外复活。
39. As an 中英文界面使用者, I want 状态、操作、确认和反馈都有一致的本地化文案, so that 不因语言影响理解。
40. As an 模板使用者, I want 删除账号的语义与清除个人信息明确区分, so that 不会误以为历史快照也被抹除。

## Implementation Decisions

### 领域与状态

- 用户包括正常及停用账号；停用不是删除，也不是强制退出的别名。已删除用户只作为保留记录中的历史身份，不是可恢复或可登录账号。
- 停用保留姓名、邮箱、密码和角色分配；允许管理员修改停用用户的角色，遵守现有角色授权和并发规则。
- 停用用户的角色分配继续计入角色使用情况。角色不可删除的保护需包含正常用户、停用用户及邀请的所有现存分配。
- 用户列表响应表达明确状态，筛选支持全部、正常、停用，默认全部；不将已删除身份混入账号列表、在线用户或角色分配选择。
- 删除可直接从正常或停用状态执行，不引入先停用、回收站、延迟删除或恢复已删除账号的产品流程。

### 权限与安全不变量

- 沿用 users.read 与 users.write。读取允许查看用户和状态；写入允许现有角色修改及新增停用、恢复、删除，不增加新权限项或新的隐式读写关系。
- 生命周期操作不比较目标与操作者权限高低：拥有用户写入权限者可以操作任意其他用户，包括 Super Admin。不得把角色分配的范围校验误用于限制停用、恢复和删除。
- 角色修改保持现有完整权限组合和授予范围规则，只有 Super Admin 能授予 Super Admin 角色。不得借生命周期功能扩大角色授予能力。
- 停用、删除本人一律拒绝，包括 Super Admin 本人。
- 可用 Super Admin 指持有该角色且未停用的用户。停用、删除、移除角色及其他影响此集合的变更不能使可用数量为零；停用中的角色持有者不能充当最后管理员保护的替代者。
- 以上保护在服务端事务和适当的锁定/版本控制下成立，覆盖并发请求，不以页面隐藏按钮或事务外计数作为唯一保护。
- 沿用现有记录版本及冲突反馈风格，避免基于旧用户状态、旧角色或已被撤销的操作者权限执行危险操作。生命周期与角色变更之间的锁顺序和认证版本语义必须一致。

### 认证、恢复与会话

- 停用提交后，全部旧会话立即不能再获得访问授权，新的登录被拒绝；在线用户统计不能继续将其有效会话计入。
- 停用期间不能申请或完成有效的密码恢复，既有重置权限失效。恢复保留原密码，但不会恢复旧会话或旧重置权限；需要重新登录或重新申请重置。
- 删除清理账号凭据、会话、重置权限、用户角色分配及不再有效的账号安全邮件任务。此类临时访问材料不属于需要保留的业务贡献。
- 认证、创建会话、密码重置完成和生命周期事务需要处理竞争，不能在停用或删除后新建有效会话、重建账号或通过恢复密码绕过状态。
- 已登录用户被停用时，在既有会话检测机制检测到失效后显示“账号已停用，请联系管理员”并返回登录页；服务端拒绝立即生效，浏览器休眠或轮询延迟不改变服务端授权结果。
- 匿名登录保留统一失败语义，匿名找回密码保留统一受理语义，不通过新增响应暴露邮箱是否存在或是否停用。已登录用户的停用提示必须基于可信的旧会话关联，不可仅凭客户端提交的邮箱或用户标识获得。
- 沿用现有 Cookie 清理、限流、Origin/CSRF 防护、服务不可用处理和会话失效机制，不将依赖故障误报为停用。
- 尚未交付的无效安全邮件应停止正常派送；已交给 SMTP 或正在发送的邮件无法保证撤回。安全保证以链接和账号访问权限已失效为准，不承诺邮件物理撤回。

### 删除、关联记录与邮箱复用

- 删除永久移除可管理账号，不保留可恢复的软删除账号，也不通过隐藏账号实现回收站。历史身份的最小保存方式由实现选择，但不能携带有效登录凭据或角色分配。
- 操作历史和其他已有业务关联不因用户删除级联清除。保留原姓名、邮箱、原用户标识，并提供已删除状态用于展示；原操作者和原目标身份都要能正确追溯，不合并为无法区分的匿名用户。
- 操作历史保留期限保持原样，不因账号删除无限延长；删除账号不是清除全部个人信息的承诺。
- 当前操作历史外键会在删除时清空操作者关联，仅保留姓名邮箱并不足以满足新要求。需要确保原用户标识在删除前后稳定可追溯，相关筛选、详情及快照展示不能改按邮箱绑定身份。
- 创建者停用或删除均不撤销邀请、不改变邀请角色、有效期限、重发/续期/撤销权限或接受规则。接受仍需满足原有的一次性、时效和角色有效性要求。
- 调整邀请创建者的删除阻塞关联，保留创建者身份快照或等价历史身份，不删除邀请，不自动转移为执行删除的管理员创建。
- 删除释放账号邮箱，之后可以重新邀请；接受后是全新的用户标识与新选择的角色，不继承旧密码、会话或历史归属。
- 删除、创建邀请和接受邀请对同一邮箱的竞争继续保证账号及邀请唯一性，不允许借竞争产生重复身份或复活原账号。
- 修改数据库结构、约束及访问层时提供可执行迁移，保证全新安装可用；不得为实施方便自动清空现有开发或预览数据库。历史快照回填应基于可获得的真实身份，不能伪造已经丢失的原用户标识。

### 页面、契约与反馈

- 在现有用户管理页面增加状态及筛选，保留原有搜索、分页和角色分配能力。筛选变化沿用现有分页重置行为。
- 按状态显示停用或恢复，两种状态都可删除。只读用户不获得写入入口；服务端独立检查权限和保护规则。
- 停用和恢复均需确认，显示可识别的目标身份。删除额外要求输入目标邮箱，显示目标姓名、邮箱、不可恢复说明及关联记录保留说明；输入不匹配不能确认。
- 不新增页面主标题、说明性副标题或重复标题。保留现有导航层级，不将此功能挪入在线用户菜单。
- 成功、失败和冲突沿用项目现有反馈模式；操作成功后刷新相关用户、角色使用情况、在线用户及其他受影响的已有查询，避免显示过时状态。
- 服务端契约需区分目标不存在、禁止操作本人、最后一位可用 Super Admin、权限不足和状态/版本冲突等可操作错误，提供中英文友好的反馈，不将业务拒绝表现为内部服务器错误。
- 无需提前固定路由命名或重复请求实现方式，但接口必须采用状态变更请求并表达目标身份与必要的并发依据，不能通过读取请求执行生命周期操作。
- 停用、恢复、删除的成功和失败沿用已有操作历史记录机制，各实际操作结果记录一次；包含动作、目标历史身份、状态变化或失败原因，不记录密码、会话令牌或重置令牌。操作历史保留现有尽力记录语义，不借此改成新的强制审计架构。
- 更新前后端契约、领域模型、权限名称说明（如有）、操作历史本地化、用户文档及生成模板相关测试。维持“强制退出 / Force sign out”与本次停用、恢复、删除的不同含义。

## Testing Decisions

- 用户已确认三个边界：以现有 HTTP 加真实 PostgreSQL 集成测试为主，复用认证/恢复/邮件测试，并以浏览器 E2E 与现有组件测试验证交互。不引入新测试框架。
- 好的测试断言公开行为、持久化结果、安全不变量与用户可见反馈，不锁定内部函数拆分、具体锁实现或调用次数。优先覆盖完整链路，仅在高层不易稳定观察的边界使用已有较低层测试。
- 参考已有访问管理 HTTP 测试、在线用户真实数据库集成测试、数据库状态集成测试及密码恢复测试，构建隔离用户和角色数据。实际运行数据库测试，不能将因缺少环境变量而跳过的测试算作通过。
- HTTP/数据库覆盖正常到停用、停用到恢复、从两种状态删除；确认凭据和有效会话失效、用户状态与列表筛选、停用用户角色仍计入使用情况，以及恢复保留当前角色与原密码。
- 权限覆盖只读/无权拒绝、用户写入可操作权限更高的目标及其他 Super Admin、角色授予仍不能越权、本人操作拒绝及最后一位可用 Super Admin 保护。
- 并发覆盖两个管理员交叉停用/删除、停用或删除与 Super Admin 角色移除竞争、角色编辑与生命周期版本冲突，以及最后可用管理员计数不能将停用管理员计入。使用真实事务和同步屏障验证结果，不靠随机睡眠碰撞。
- 身份保留覆盖原操作者和原目标在删除前后的姓名、邮箱、原用户标识、删除标记与历史筛选；验证历史记录仍受既有保留策略约束，不能因删除混同不同用户。
- 邀请覆盖创建者停用和删除后邀请仍可查看、管理和接受；保留创建者历史身份；已有过期、撤销及角色范围规则继续生效。
- 邮箱复用覆盖删除后重新邀请、接受后新用户标识与新角色、原历史不绑定新账号，以及删除与邀请/接受的并发唯一性。
- 认证与恢复覆盖停用提交后旧会话不可用、停用后登录拒绝、旧重置链接失效、停用期间恢复入口不产生有效权限、恢复后旧会话/链接仍失效、新申请可以正常工作。
- 匿名接口覆盖存在/不存在/停用邮箱的响应不引入状态泄露；已登录停用提示仅能依据可信会话获得；依赖不可用不被误判为账号停用。
- 邮件覆盖待发送安全邮件的无效化及已领取邮件竞争，确认即使邮件到达，失效链接也不能重新开放访问；不测试或承诺已发送邮件可撤回。
- 浏览器 E2E 复用认证和在线用户场景，至少使用两个独立浏览器上下文验证管理员停用另一用户后，对方检测到失效、看到停用提示并返回登录页；恢复后必须重新登录。
- 浏览器及组件覆盖状态筛选、正常/停用对应动作、删除邮箱确认、取消无副作用、待处理状态避免重复提交、成功/失败反馈、不可操作本人及最后管理员保护提示，并验证中英文文案。
- 数据库迁移验证使用独立一次性数据库，运行完整迁移并验证真实约束及持久化。涉及原结构到新结构的迁移时使用受控旧结构测试数据验证身份保留和邀请关联，不触碰用户现有预览数据。
- 执行现有前后端检查、测试、构建与生成模板相关检查；端到端测试需启用对应开关并实际执行。报告实际运行结果及任何环境限制。

## Out of Scope

- 批量停用、恢复、删除，回收站，延迟删除，恢复已删除账号。
- 新增生命周期专用权限、改变现有读写独立模型或放宽角色授予范围。
- 停用或删除本人、自助注销账号。
- 将删除账号等同于个人信息彻底清除、匿名化所有历史或法律合规认证。
- 删除用户及其全部贡献的第二种删除模式、级联删除邀请或业务数据。
- 多租户、组织负责人迁移、通用所有权转移平台、针对尚不存在业务模块的通用关联处理框架。
- 新增独立已删除用户管理页、自动按邮箱合并新旧身份。
- 新的邮件通知产品、邮件物理撤回、独立推送基础设施或操作历史架构重做。
- 自动清空、重建现有开发或预览数据。
