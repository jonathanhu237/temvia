# 模板交付可靠性与 SMTP 凭据复用边界

Status: open
Labels: ready-for-agent

## Problem Statement

Temvia 已具备后台项目起点所需的主要能力，但当前发布检查没有证明新用户能按文档完成首次安装：迁移镜像漏打包用户生命周期迁移，空库初始化后停留在第 9 版，而 API 要求第 10 版，导致启动失败。生成器文档将 Git 描述为可选，但实际缺少 Git 时无法生成项目。升级说明未包含新镜像构建，可能让更新源码后的部署继续运行旧版本。

邮件配置管理允许管理员使用已有 SMTP 凭据，但不应包含取出已有凭据的能力。当前测试和保存路径在改变服务器或登录账号后仍可复用原密码，导致有邮件配置权限的人能够把原密码发往自己控制的服务器。

本次目标是让模板成为可用于正式项目的可靠起点，而不是建设完整生产运维平台。

## Solution

修复迁移镜像内容，保证按首次运行指南能将空数据库迁移到当前 API 要求的版本。让 Git 真正可选，并保留 Git 可用时对现有仓库和用户文件的保护。

收紧已保存 SMTP 密码的复用边界：更换邮件服务器或登录账号后不能隐式携带原密码；需要密码认证的新连接必须重新填写密码。连接身份不变时，修改发件人名称等信息不要求重复输入密码。测试邮件与保存配置执行同一规则，不增加权限类型或后台警告系统。

在发布前对同一实际发布包执行完整首次使用验收：生成独立项目、构建容器、初始化空数据库、启动 API 和前端，并通过浏览器创建管理员、登录。任一步失败阻止发布。补全中英文停机升级说明，明确构建新镜像的顺序。

## User Stories

1. As a 新项目开发者, I want 从发布包生成可以实际运行的项目, so that 我不必先排查模板自身的交付缺陷。
2. As a 新项目开发者, I want 在生成目录中独立构建容器, so that 项目不依赖 Temvia 源码工作目录或维护者机器上的产物。
3. As a 首次部署者, I want 迁移镜像包含所有当前迁移, so that 空数据库可以达到 API 要求的版本。
4. As a 首次部署者, I want 按指南启动 API 和前端, so that 我能够进入管理员初始化页面。
5. As a 首次部署者, I want 从 API 日志获取临时初始化链接并完成管理员创建, so that 我不需要直接写数据库来获得初始账号。
6. As a 首次部署者, I want 初始化后显式登录并进入受保护的后台, so that 我能确认整个首次使用流程可用。
7. As a 维护者, I want 未来新增迁移也自动进入迁移镜像, so that 不会再次因为手工枚举遗漏导致发布不可运行。
8. As a 未安装 Git 的开发者, I want 正常生成完整项目并获得成功退出状态, so that 版本管理工具不会阻止我使用模板。
9. As a 未安装 Git 的开发者, I want 得知项目未初始化 Git 仓库, so that 我可以自行决定何时启用版本管理。
10. As a 已安装 Git 的开发者, I want 独立项目继续自动初始化仓库, so that 保留现有便利性。
11. As a 现有仓库的维护者, I want 在仓库内生成项目时不产生嵌套仓库且不更改暂存区或提交历史, so that 原仓库不受破坏。
12. As a 使用者, I want 真正的 Git 检查错误仍被明确报告, so that 损坏仓库等问题不会被误当成未安装 Git 而忽略。
13. As a 使用者, I want 非空目录和已有文件继续受到生成器保护, so that Git 可选不会削弱生成安全性。
14. As a 超级管理员, I want 授予邮件配置管理能力而不授予取出原 SMTP 密码的能力, so that 已有提供商凭据不会因委托配置而泄露。
15. As a 邮件配置管理员, I want 在原服务器和原登录账号不变时保留已保存密码, so that 修改发件人名称或邮件语言时无需重复输入。
16. As a 邮件配置管理员, I want 更换服务器或登录账号后被要求提供新的密码, so that 原密码不会自动发送到新的连接身份。
17. As a 邮件配置管理员, I want 测试邮件和保存配置遵守同一凭据规则, so that 测试入口不能绕过保存时的保护。
18. As a 邮件配置管理员, I want 凭据输入有问题时通过现有表单反馈知道如何修正, so that 不需要新增后台提示系统。
19. As a 邮件配置管理员, I want 失败的测试或保存不改变已保存配置和正在使用的邮件配置, so that 无效操作不会破坏现有服务。
20. As a 邮件配置管理员, I want 继续显式清除凭据并使用原本允许的无认证连接, so that 本次修复不强迫所有 SMTP 服务采用密码认证。
21. As a 发布维护者, I want 验收安装自实际打包产物的 CLI, so that 检查覆盖用户真正获得的内容。
22. As a 发布维护者, I want 在独立空数据库和新建容器中执行首次启动验收, so that 旧镜像、旧数据或已有管理员不会掩盖缺陷。
23. As a 发布维护者, I want 浏览器真正完成初始化和登录而不是仅检查首页返回成功, so that API、代理、前端及会话流程都经过验证。
24. As a 发布维护者, I want 任一必要验收失败就阻止 npm 发布, so that 不可用的版本不会进入公开分发。
25. As a 发布维护者, I want 保留现有类型检查、单元测试、Git 测试和打包测试, so that 新增门禁不会替代已有回归保护。
26. As a 发布维护者, I want 测试结束后自动清理隔离资源并留下不泄露秘密的诊断信息, so that 失败可排查且不会污染后续运行。
27. As a 已部署项目的维护者, I want 升级指南明确停止 API、备份、构建、迁移和启动的顺序, so that 新源码真正进入运行中的服务。
28. As a 已部署项目的维护者, I want 迁移失败时停止继续启动新服务, so that 不会运行数据库版本不兼容的 API。
29. As a 中文或英文读者, I want 两种语言的依赖、首次使用和升级说明一致, so that 不会因阅读语言不同而遗漏必要步骤。

## Implementation Decisions

- 本轮属于交付和既有行为修复，不新增业务模块，不调整角色、权限目录或会话模型，也不需要新的业务数据库迁移。
- 迁移镜像必须包含当前全部正向与逆向迁移，并避免新增迁移后仍需维护容易遗漏的逐文件名单。保持显式执行迁移与 API 严格校验数据库版本的现有设计，不通过降低版本要求绕过缺陷。
- 将已有 SMTP 凭据视为绑定于原服务器和原登录账号的秘密。服务器身份包括主机与端口；登录账号按现有输入规范化规则比较，不对用户名引入不受支持的大小写折叠。名称不同的主机不因当前解析到同一 IP 而被视为同一身份。
- 当上述身份变化且请求省略密码时，禁止复用已有密码。新的密码认证连接要求显式提供非空密码；保持现有用户名与密码配对、显式清除密码及无认证配置规则。修改显示名称、发件人信息或邮件语言不触发重填。
- 保存和测试必须共用一致的复用规则；测试在执行外部邮件发送前拒绝违规输入，保存被拒绝时不得更新持久化配置或运行时邮件配置。继续执行现有版本冲突保护，测试邮件不保存配置。
- 继续加密存储 SMTP 密码，不在读取响应、错误、日志或表单回填中暴露密码。沿用现有 API 验证错误和表单反馈机制，必要时补充中英文错误文案，不新增后台警告或通知机制。
- SMTP 加密策略保持现状，包括生产环境保存时的既有校验。本轮不增加启动或发送阶段的检查，也不放开生产环境不加密选项；讨论中曾提及的这些替代方案均未纳入最终范围。
- Git 可执行文件确实缺失时，跳过仓库初始化，完成正常生成并提示未初始化 Git。Git 可用时仍保留独立仓库初始化、现有工作树与 linked worktree 保护、继承 Git 环境变量隔离，以及不自动暂存或创建提交的行为。
- Git 缺失与其他执行或仓库检查错误必须区分。超时、权限错误、损坏的仓库元数据等不能被当作“Git 可选”而静默吞掉；保留现有目标目录验证、预检、写入与保守清理保证。
- 新增首次使用发布门禁接入现有发布流水线，必须在公开发布前完成；不改变当前分支、版本计算和自动发布政策。
- 门禁安装并调用将要发布的真实 tarball 中的生成器，在源码树之外生成项目，使用新项目的 Compose 配置构建和运行。不得以本地模板挂载、直接补执行遗漏 SQL 或已有宿主二进制绕过产物内容问题。
- 首次使用门禁使用隔离 Compose 项目、空数据库卷、独立端口和临时随机密钥，按文档路径构建全部必要镜像、执行迁移、启动 API 与前端；浏览器公共 origin 与 API 配置一致。
- 管理员初始化凭据从实际 API 日志中的初始化链接获取，随后由浏览器执行创建和显式登录，验证进入受保护页面及有效会话。不得预先插入管理员或注入会话替代验收步骤。
- 继续发布与验收相同的已校验 tarball，不在验收之后重新打包另一份内容。保留已有发布后公开生成入口检查，它不能替代发布前运行验收。
- 首次使用检查应有有界就绪等待和总超时，失败阻断发布；无论成功失败均清理临时容器与卷。必要诊断信息不得包含初始化 token、会话、密码或其他秘密。
- 升级指南采用用户已确认的停机方案：停止 API，备份数据库，构建新镜像，显式执行迁移，再启动 API 和前端。构建应涵盖迁移、API 和前端镜像；失败不得继续后续部署步骤。保留密钥备份、数据卷保护和审慎回滚说明。
- 更新中英文文档及本轮修复说明；只陈述实际验证的平台范围，不把 Linux CI 上的单一路线验收扩大为 Windows 或所有生产环境的兼容承诺。

## Testing Decisions

- 测试应检查对用户可观察的结果：生成结果与退出状态、配置是否被接受、是否向新连接提供旧秘密、实际镜像是否能完成迁移、浏览器能否初始化并登录。避免绑定私有函数名称、内部调用次数或易变 DOM 结构。
- 最高层测试入口采用已经在讨论中确认的“实际发布包 → 独立项目 → Compose 首次启动 → 浏览器初始化与登录”。这个入口同时覆盖打包、生成、迁移镜像、API、前端代理和会话，不另造一套脱离交付产物的验收实现。
- 复用现有 tarball 安装及生成测试的临时目录模式，复用现有 Playwright 基础设施与认证操作。现有 E2E 含可选环境变量和可能随页面变化失效的断言；必要验收不得因缺少环境变量被跳过，也不得以无关的固定首页标题代替真实登录结果。
- Compose 回归必须用原样生成的镜像及空数据库证明迁移达到 API 要求且初始化可用。额外验证迁移镜像包含所有已发布 SQL 迁移；故意缺失迁移时门禁必须失败，而不是在验收脚本中补齐。
- SMTP 复用测试复用邮件配置应用服务已有的存储、加密和邮件发送适配器测试替身，在该服务公开操作上验证规则；复用现有设置页面组件测试验证错误可理解、修正后可重试，不需要真实公网 SMTP。
- SMTP 用例覆盖：身份不变时省略密码成功；仅修改发件人名称或语言仍成功；分别改变主机、端口、用户名且省略密码时，测试和保存均拒绝；显式提供新密码后使用新凭据而非旧凭据；清除密码和无认证配置保持现有合法性；过期版本不能复用当前密码；拒绝不改变保存状态与运行时配置。测试替身确认被拒绝操作没有把旧密码交给新的 SMTP 连接。
- Git 测试复用现有 CLI 子进程、Git runner 和真实 Git 临时仓库入口。将“缺少 Git 必须失败”的旧预期改为成功生成、无新仓库和明确提示，同时保留现有工作树、linked worktree、非空目录、损坏元数据和初始化失败等回归用例。
- 保留并运行现有生成器、发布规则、tarball、Go 和前端检查。涉及数据库行为的验证在隔离且完整迁移的 PostgreSQL 上运行，显式提供测试连接信息，不把未启用数据库的跳过结果记为集成测试通过；这不等于要求本轮把所有既有浏览器 E2E 都扩展为发布门禁。
- 对升级说明做有旧镜像缓存的运行验证：仅更新源码后按新顺序执行，确认迁移及服务实际使用重新构建的版本，数据得到保留。核对中英文步骤一致、构建覆盖迁移镜像，且不包含无意删除数据库卷的操作。
- 实施验证遵循项目工作流：源码修改及 Git 操作在本地，单向同步隔离副本至 Centaurus 执行资源密集型构建和测试；暴露测试服务时转发本地端口用于验证。不得碰现有项目数据库或复用其管理员与秘密。

## Out of Scope

- 改变 SMTP TLS/不加密选项、生产保存校验，新增启动或发送阶段安全限制。
- 登录时间差和账号枚举防护改造。
- 恢复或新增后台操作警告、横幅、通知中心。
- 新增 SMTP 权限类型、拆分系统设置角色或重新设计邮件凭据保管系统。
- 引入自动升级、零停机迁移、自动回滚或模板自动更新机制。
- 提供完整 HTTPS、备份调度、监控告警或生产基础设施方案。
- 全量重构、修复所有不相关既有 E2E，或要求所有浏览器测试一律进入本轮发布门禁。
- 新增业务功能、更换技术栈、扩大跨平台支持承诺。
- 自动提交、推送或公开发布；这些不是编写本规格所授权的操作。
