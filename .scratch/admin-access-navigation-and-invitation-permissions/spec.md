# 管理端用户、邀请与角色信息架构及邀请权限

Status: implemented
Labels: ready-for-agent

## Problem Statement

管理端目前把已激活用户和邀请放在同一个页面中，而角色位于另一个一级菜单。用户、邀请和角色实际上属于同一个访问控制领域，但当前导航没有表达这种关系；用户页还同时承担用户浏览、角色分配、邀请创建和邀请生命周期管理，随着筛选、排序和操作增加，页面会越来越拥挤。

角色表格也没有把最重要的信息表达清楚。“类型”列与角色名称下方的“内置角色／自定义角色”标签重复，占用了空间；权限数量只能看到数字，无法查看实际权限；分配数量没有说明同时包含用户和邀请；内置角色为什么不能编辑只能通过尝试操作后得知。角色页如果继续加入已分配人员清单，还会与用户和邀请页面重复。

邀请目前只允许 Super Admin 查看和管理，权限目录中没有表达邀请职责。只授予用户读取权限或角色读取权限的管理员无法被单独授权查看邀请，也无法被安全地委派邀请管理。直接开放现有邀请操作又会产生权限提升风险：邀请管理员可能为新账号分配超过自身权限的角色，甚至分配 Super Admin。

用户需要一套清晰的信息架构：在统一的“用户与权限”导航组下，分别管理已激活用户、邀请和角色；每个页面只承担一种职责；角色详情可以直接查看；邀请查看和邀请管理成为明确、可组合且由后端强制执行的权限。

## Solution

Dashboard 侧边栏新增可折叠的“用户与权限／Users & Access”父菜单。父菜单本身没有页面，下面使用简短的“用户／Users”“邀请／Invitations”“角色／Roles”三个子菜单；对应页面标题使用“用户管理／User management”“邀请管理／Invitation management”“角色管理／Role management”。当前位于任一子页面时父菜单保持展开，并根据当前账号权限只显示可访问的子页面。

用户管理页只显示已激活用户，邀请管理页只显示尚未接受的邀请，角色管理页只显示角色定义。三个页面继续使用 shadcn Data Table，分别提供与任务匹配的搜索、筛选、排序、分页和操作。邀请用户的入口只出现在邀请管理页。现有角色、用户角色和邀请表单继续使用弹窗及内存草稿；这次信息架构调整不改变已经确定的草稿生命周期和乐观锁行为。

角色表格移除“类型”列和角色名称下方的类型标签。内置角色只在名称旁显示可访问的锁图标，并通过提示说明其不可编辑或删除。点击角色名称或操作菜单中的“查看详情”会打开只读详情弹窗，展示完整名称、描述、内置状态、分配数量，以及按资源分组并本地化的权限名称和说明。角色页不展示具体用户或邀请身份。

权限目录新增 `invitations.read` 和 `invitations.manage`。邀请读取依赖用户读取；邀请管理依赖邀请读取、用户读取和角色读取。角色编辑器自动补齐并锁定依赖权限，服务端也对权限集合做传递性补齐，确保任何客户端都不能保存不完整的依赖关系。

拥有邀请读取权限的管理员可以查看全部邀请。拥有邀请管理权限的管理员可以创建、重新发送、续期和撤销邀请，但只能创建或操作其有权分配的邀请：所选角色的合并权限不能超过管理员自己的有效权限，且只有 Super Admin 可以分配 Super Admin 角色。该限制由服务端强制执行，界面同时过滤不可分配角色并解释不可执行的邀请操作。

## User Stories

1. 作为管理端用户，我希望在一个“用户与权限”导航组中找到用户、邀请和角色，以便理解它们属于同一个访问控制领域。
2. 作为管理端用户，我希望父菜单可以折叠和展开，以便控制侧边栏占用空间。
3. 作为管理端用户，我希望父菜单本身不打开一个重复的汇总页，以便直接进入具体任务。
4. 作为中文用户，我希望侧边栏显示“用户与权限”“用户”“邀请”“角色”，以便名称简短且容易扫描。
5. 作为英文用户，我希望侧边栏显示“Users & Access”“Users”“Invitations”“Roles”，以便名称自然且一致。
6. 作为进入任一访问管理页面的用户，我希望“用户与权限”父菜单保持展开，以便知道自己位于哪个导航层级。
7. 作为权限受限的管理员，我希望只看到自己可以访问的子菜单，以便导航与实际权限一致。
8. 作为至少能访问一个子页面的管理员，我希望仍能看到“用户与权限”父菜单，以便进入获准页面。
9. 作为不能访问任何相关页面的用户，我希望整个“用户与权限”导航组不出现，以便避免无效入口。
10. 作为直接访问无权页面地址的用户，我希望看到标准无权限反馈，以便理解访问失败的原因。
11. 作为用户管理员，我希望用户管理页只显示已激活用户，以便列表中的每一行都代表可以登录的账号。
12. 作为用户管理员，我希望用户表展示姓名、邮箱、角色、创建时间和操作，以便快速理解账号信息。
13. 作为用户管理员，我希望用户表不显示状态列，以便不为全部相同的“已激活”状态占用空间。
14. 作为查找用户的管理员，我希望按姓名或邮箱搜索全部用户，以便找到当前页之外的记录。
15. 作为浏览用户的管理员，我希望按角色排序用户，以便快速比较不同角色的已激活用户。
16. 作为浏览用户的管理员，我希望默认按创建时间从新到旧排列，以便优先看到新账号。
17. 作为浏览用户的管理员，我希望可以按姓名、邮箱、角色和创建时间排序，以便采用适合当前任务的顺序。
18. 作为修改搜索或排序的管理员，我希望列表回到第一页，以便不会停留在已经失效的游标位置。
19. 作为查看角色较多用户的管理员，我希望表格最多直接显示两个角色标签并以“+N”收起其余角色，以便表格行保持紧凑。
20. 作为使用鼠标或键盘的管理员，我希望可以从“+N”查看完整角色列表，以便不会因收起显示而丢失信息。
21. 作为用户管理员，我希望姓名保持普通文本并使用明确的“管理角色”操作，以便不会误以为点击姓名会打开个人资料。
22. 作为有权管理用户角色的管理员，我希望从操作列打开角色分配弹窗，以便修改用户的角色。
23. 作为只有用户读取权限的管理员，我希望能查看用户但看不到角色修改入口，以便页面准确反映只读权限。

25. 作为邀请管理员，我希望在邀请管理页右上角看到“邀请用户”按钮，以便从负责邀请的页面开始操作。

## Implementation Decisions

- **范围与现状**：修改管理端访问控制信息架构、角色展示、邀请查询与授权策略。沿用现有 React、TanStack Router、TanStack Query、TanStack Table、shadcn/Radix、Zustand、Go HTTP API 和 PostgreSQL 体系。
- **导航结构**：新增可折叠且无独立落地页的“用户与权限／Users & Access”父菜单。子菜单顺序固定为用户、邀请、角色；侧边栏用短名称，页面标题用管理名称。访问子路由时父菜单保持展开。
- **权限驱动导航**：用户页要求 `users.read`，邀请页要求 `invitations.read`，角色页要求 `roles.read`。拥有任一子页面权限才显示父菜单。直接访问无权路由时由现有标准无权限反馈处理，隐藏菜单不是安全边界。
- **页面拆分**：当前混合的用户与邀请界面拆成独立页面和独立查询状态。用户页只加载用户；邀请页只加载邀请及完成邀请操作所需的数据；角色页继续独立加载角色和权限目录。
- **用户表**：列为姓名、邮箱、角色、创建时间、操作，不增加状态列。姓名不再作为隐式操作入口；角色修改只从明确的“管理角色”操作打开。保留服务端姓名／邮箱搜索、稳定游标分页和默认创建时间倒序，用户表不提供角色筛选，新增按角色名称序列的服务端排序。多个角色按表格中的确定顺序组成排序键，相同排序值继续使用用户 ID 保持稳定次序。
- **紧凑角色标签**：用户和邀请表最多直接显示两个角色标签，其余以“+N”表示。完整列表通过同时支持鼠标悬停和键盘聚焦的提示展示，并提供可访问文本。
- **邀请表**：列为姓名、邮箱、角色、状态、操作。状态根据当前时间和到期时间分为待接受、已过期，并在同一单元格显示具体到期时间。邮件语言不占独立列，在邀请创建表单和重新发送／续期确认中显示。
- **邀请查询**：保留服务端姓名／邮箱搜索、稳定游标分页和默认创建时间倒序，新增角色与状态筛选。可排序字段为姓名、邮箱、创建时间和到期时间。搜索、筛选或排序变化会重置游标。
- **邀请状态语义**：接受邀请后记录转为用户并从邀请列表消失。过期不会删除邀请，也不会移除角色分配。重新发送待接受邀请或续期已过期邀请使用相同领域操作：废弃旧链接、生成新链接、重置到期时间，并沿用原邀请邮件语言。
- **邀请操作**：邀请创建入口只位于邀请页。待接受邀请显示重新发送和撤销；已过期邀请显示续期并发送和撤销。重新发送／续期确认展示邮箱、邮件语言及旧链接将失效；撤销继续使用应用内确认。
- **角色表**：最终列为角色名称、描述、权限数量、分配数量、操作。移除类型列和名称下方的内置／自定义副标签。名称、权限数量和分配数量可排序；名称可搜索；描述保留并在单元格中截断。
- **内置角色标识**：只有内置角色在名称旁显示锁图标。图标的悬停与键盘聚焦提示说明“Temvia 提供的内置角色，无法编辑或删除”，并有屏幕阅读器名称。角色详情中以可见文字显示内置状态，覆盖触摸设备场景。自定义角色不显示类型标识。
- **角色详情**：角色名称和操作菜单中的“查看详情”都打开只读 Dialog。详情展示完整名称、描述、内置状态、权限数量、分配数量，以及按资源分组的权限。权限只显示本地化产品名称和说明，不显示内部权限键。自定义角色在有权管理时可以从详情进入现有编辑 Dialog。
- **角色操作**：内置角色操作菜单只有查看详情；自定义角色菜单包含查看、编辑、删除。只读角色查看者不看到创建、编辑或删除。角色页不展示用户或邀请身份，也不从分配数量提供跳转。
- **分配数量**：分配数量是用户角色分配与邀请角色分配之和。待接受和已过期邀请都计入，直至邀请被接受或撤销。表头信息图标解释计数和删除约束。存在分配时删除项置灰并说明处理方式；服务端仍以关联约束和领域冲突作为最终保护。
- **权限目录**：新增 `invitations.read`，资源为 invitations、动作为 read，中文产品名为“查看邀请”，说明为“查看邀请、状态及预分配角色”；新增 `invitations.manage`，资源为 invitations、动作为 manage，产品说明覆盖创建、重新发送、续期和撤销邀请。
- **权限依赖**：`invitations.read` 传递性依赖 `users.read`；`invitations.manage` 依赖 `invitations.read`、`users.read` 和 `roles.read`。权限目录需要能表达依赖关系，角色输入在领域边界被规范化为依赖闭包，持久化和返回的自定义角色权限必须完整且可预测。
- **角色编辑器依赖交互**：选择上层权限时自动选择并锁定当前必需的依赖项；取消上层权限时解除依赖项锁定但不自动取消它们。权限仍按资源分组展示，并为锁定状态提供原因说明和可访问描述。
- **内置角色**：Super Admin 继续在运行时展开为实时权限目录中的所有权限，因此自动获得两项新权限。代码库目前只有 Super Admin 是内置角色；名为 Preview Viewer 的现有预览数据属于自定义角色，不能按名称赋予特殊系统语义。预览环境中的该角色应显式加入 `invitations.read` 及其依赖，但不加入 `invitations.manage`。
- **邀请读取授权**：`invitations.read` 允许读取全部邀请及其中的角色名称、状态和邮件语言数据。由于它依赖 `users.read`，持有者同时可以进入用户页；没有 `roles.read` 时不能进入角色管理页或查看权限定义。
- **邀请管理授权**：`invitations.manage` 允许创建、重新发送、续期和撤销邀请，不允许修改已激活用户的角色或修改角色定义。所有邀请写接口从 Super Admin 专属检查改为该权限与角色上限的组合检查；Super Admin 继续不受上限限制。
- **可分配角色规则**：非 Super Admin 管理员所选全部角色的权限并集必须是该管理员有效权限集合的子集，相等允许；Super Admin 角色无条件排除。服务端在创建邀请前加载并规范化所选角色后执行检查，不能信任客户端提供的候选列表。
- **既有邀请操作规则**：拥有邀请读取权限的管理员能看见所有邀请。非 Super Admin 只有在邀请现有角色集合符合其可分配角色规则时，才能重新发送、续期或撤销；不符合时 API 拒绝写入，界面保留记录并将操作置灰，解释需要更高权限。
- **查询与授权 API**：用户列表查询保留角色标识条件的接口兼容性，并新增角色名称序列排序；邀请列表查询增加角色标识和待接受／已过期状态条件。查询条件和排序边界必须参与游标签名或校验，避免复用其他查询生成的游标。邀请写入错误沿用标准 Problem Details，并为不可分配角色或不可管理邀请提供稳定错误代码。
- **数据模型**：不需要新增用户、角色、邀请或关联表。权限键仍存储在现有角色权限关系中；新增数据库迁移只处理新权限相关的受控数据更新，不对任意同名自定义角色赋予权限。状态由到期时间计算，不增加可漂移的状态列。
- **客户端权限模型**：当前用户投影继续返回有效权限和 Super Admin 标记。导航和操作能力从这些权限推导；邀请页面分别区分可查看和可管理，用户与角色修改能力继续遵循现有 Super Admin 限制。
- **草稿与并发**：移动邀请表单、角色表单和用户角色弹窗时保留既有 Zustand 内存草稿规则、账号隔离、成功清理、失败保留和提交中防重复行为。角色编辑和用户角色分配继续使用现有乐观锁；本次不新增可编辑邀请字段。
- **本地化与可访问性**：新增中英文导航、页面标题、列名、状态、权限名称、权限说明、提示、确认和错误文案。Dialog、Dropdown Menu、Tooltip、筛选控件和折叠菜单沿用现有焦点管理、键盘操作与屏幕阅读器语义。窄屏下允许表格横向滚动或按现有策略保持关键操作可达。
- **兼容性**：此前已经完成的外观、语言按钮、Data Table、Dialog、Zustand 草稿和乐观锁实现继续保留。本 Spec 取代旧 Spec 中关于用户与邀请同页、角色类型列和邀请仅限 Super Admin 的描述，不改变认证页偏好入口。

## Testing Decisions

- 测试只断言用户可观察行为、HTTP 授权结果和持久化查询语义，不断言组件内部状态、具体 Hook 调用、CSS 类名或 SQL 实现细节。
- **管理端 React 集成接缝**：沿用现有访问管理组件测试及 QueryClient/API mock 方式，覆盖权限驱动的父子导航、用户／邀请／角色独立页面、最终表格列、角色列排序、用户页不显示角色筛选、紧凑角色标签、筛选重置、角色详情、内置角色提示、只读状态、邀请确认和不可执行操作说明。
- 管理端测试应以可访问角色、名称和用户操作驱动界面，验证鼠标与键盘可发现的信息，不通过 DOM 结构选择器绑定组件实现。
- **API HTTP 权限矩阵接缝**：扩展现有 HTTP permission matrix，加入仅有 `users.read`、拥有 `invitations.read`、拥有 `invitations.manage`、权限不完整角色、普通角色管理员和 Super Admin 等主体。
- HTTP 矩阵覆盖邀请列表可见性、邀请创建／重发／续期／撤销、权限依赖闭包、相等权限委派、越权角色组合、Super Admin 分配限制、对高权限既有邀请的写入拒绝，以及拒绝请求不触碰存储写操作。
- 角色创建与更新测试验证 API 输入缺少依赖项时返回的角色和持久化结果都包含完整依赖闭包；移除上层权限后不应由服务端擅自移除仍由客户端保留的读取权限。
- **PostgreSQL 集成补充接缝**：只补充上层无法证明的查询行为，包括用户按角色名称序列排序及跨页游标、角色筛选先于游标分页、邀请状态以查询时刻计算、过期邀请仍计入分配数量、撤销后数量减少、接受邀请后邀请分配转换为用户分配，以及筛选条件与游标不匹配时被拒绝。
- 既有访问组件测试是表格、Dialog、草稿和乐观锁的前端先例；既有 HTTP 权限矩阵是读取与写入授权的 API 先例；既有 RBAC 与邀请生命周期 PostgreSQL 集成测试是关联数量和邀请转换的存储先例。
- 不为简单的组件拆分、路由文件名称或权限常量本身编写镜像实现的单元测试。只有在权限依赖闭包无法通过 HTTP 矩阵清晰定位失败时，才增加针对领域权限目录的窄单元测试。

## Out of Scope

- 不修改登录页、认证页或 Dashboard 顶栏已经完成的外观与语言双按钮。
- 不把外观或语言偏好改为跨设备账号设置。
- 不增加修改密码、个人资料或其他账号设置。
- 不新增 `users.manage` 或 `roles.manage`；已激活用户角色和角色定义的修改继续只允许 Super Admin。
- 不允许编辑邀请的姓名、邮箱、邮件语言或预分配角色；需要变化时撤销并重新创建邀请。
- 不增加批量邀请、批量重发、批量撤销或批量修改用户角色。
- 不在角色页展示或搜索具体用户、邀请和分配身份，也不从分配数量跳转到另一个页面。
- 不创建统一的用户与邀请合并表，也不增加“未激活用户”这种混合领域状态。
- 不把 Preview Viewer 变成按名称识别的内置角色，也不自动修改生产环境中任意同名自定义角色。
- 不改变邀请接受、密码设置、邮件投递和链接加密机制，只沿用重新发送时替换链接与到期时间的既有行为。
- 不为邀请重新发送和撤销增加乐观锁版本输入；邀请没有可编辑详情，本次依赖服务端当前记录及授权检查处理并发操作。

## Further Notes

- 现有已完成的管理端外观、语言与访问管理 Spec 保留为历史记录。本 Spec 是后续增量改造，并明确覆盖旧文档中已不再成立的访问管理页面结构。
- 代码库的内置角色模型目前只认可 `super_admin`。讨论中提到的 Preview Viewer 来自运行或预览数据，不是当前数据库模型中的内置角色；实施时应更新受控的预览数据，而不能引入基于显示名称的授权分支。
- `invitations.manage` 的角色上限是安全边界，不只是界面便利功能。所有邀请写操作必须在可信服务端使用规范化后的当前主体和角色权限重新判断。
- 邀请状态筛选以服务端查询时刻为准。长时间停留页面后，客户端可以在显示层重新判断到期状态，但刷新查询后必须与服务端筛选结果一致。
